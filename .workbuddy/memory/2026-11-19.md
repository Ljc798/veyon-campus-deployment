## 16:15–17:00 局域网发现失败定位 + 1.1.84（CloudBase 恢复、后台恢复）

### 现场
- 教师端确实在分发：`curl http://192.168.31.39:39178/v1/health` 返回
  `{"campus":"智学前程-测试1119","packageId":"917e7bb7-...","sizeBytes":5882}`，
  目录里的 `downloadUrl` 也按请求网卡回填成 192.168.31.39。因此问题在"学生端没找到"，不在服务端。
- 本机接口：以太网 192.168.31.39/24，`vEthernet (Default Switch)` 172.21.160.1/20。

### 根因（两处假设都不成立）
1. `FindLocalClassroomAddress()` 取"第一个私有 IPv4"——WSL/Hyper-V/VMware 的虚拟网卡常常排在前面，
   于是扫的是虚拟网段的 /24。
2. `EnumerateClassroomTargets` 写死 /24。Default Switch 是 /20，虚拟机可能在 172.21.161.x，
   而宿主（=教师机）是 172.21.160.1，两个 /24 不同，永远扫不到。
3. 学生端没有手填地址的入口，扫描失败即死路。

### 实现
- 新增 `ClassroomNetwork(Address, PrefixLength, Gateway)` 与 `FindClassroomNetworks()`：
  有默认网关的真实网卡排前，虚拟网卡靠后。
- `EnumerateClassroomTargets(address, prefixLength)` 按真实前缀枚举，上限 4094（/20），
  更大（如 /16）回退到本机 /24。
- `FindProvidersAsync(networks, extraTargets)` **两段式**：先探网关 + 本机 /24（2s 超时），
  没命中才展开大网段（800ms 超时、128 并发）。NAT 虚拟机里网关就是宿主，第一跳即命中。
- 学生端窗口加"教师机 IP"输入框（`LanTeacherAddress`，回车即连），失败提示列出实际扫过的网段。
- 测试：新增 /24=253、/23=509、/20=4093、/16 回退 253 的断言；端口被占用时 LAN 固件改为 SKIP 而非崩溃。

## 20:00 策略推送"时好时坏"的根因与修复

### 症状
- 手机端推送策略有时成功、有时无效；教师端教室页推送也不稳，只有"策略与预设"页基本可用。

### 根因
- 三条策略通道（网站 / 应用 / 长期系统）都把单台整体超时设成 6 秒、并发 16：
  `WebsitePolicyRuntime.cs:4351`、`ApplicationPolicyTransport.cs:246`、`StudentSystemPolicyTransport.cs:39`。
- 学生端是**先落盘再回执**，教室机忙着应用上一条策略时会超过 6 秒；中继通道自身等 30 秒，
  客户端 6 秒先掐断 → 整台判失败，且没有重试。
- 16 路并发同时打一间教室的交换机，进一步把每台都拖慢。教室页与手机推送发生在课堂轮询、
  画面预览等并流之中，所以比"策略与预设"更容易踩线，表现为"时好时坏"。
- 课堂快捷管控的网站限制同样走 `WebsitePolicyTransport.PushAsync`（`TeacherClassroomQuickControlService.cs:693/985/1336`），
  所以教室页也一起受影响。

### 改动（未发版，属于 1.1.86 范围）
- 三个通道：单台超时 6→20 秒，并发 16→8；`ApplicationPolicyTransport` 新增 `PolicyPushTimeout` /
  `PolicyPushParallelism`，读取类调用仍是 6 秒/16 并发。
- 超时文案改为可操作的说明（"学生端可能仍在应用上一条策略，等十几秒再推一次"），
  `StudentSystemPolicyTransport` 不再直接抛 HttpClient 原文。
- 教师端/学生端各编译 0 错误。固件检查在本机无法运行：公共前置要调 `sc.exe`，被沙箱程序黑名单拦截
  （`Veyon 探测状态非法：unknown`），与本次改动无关。

## 22:45–23:10 教室按钮“过一手才可用” + 学生端静默更新卡死（1.1.88）

### 现象 1：启用网站限制按钮灰色，点过一次“锁定键鼠/取消”后才可点
- 四个派生属性共用同一个 gate（`CanStartClassroomQuickControl`），但 `RefreshClassroomSessionProperties`、
  `RoomProfiles` setter、`SetVeyonDeviceDirectoryReadValid`、两处 scope 变更只发了其中一两个 `Changed`，
  按钮绑定因此停在旧值，直到别的操作补发了漏掉的那个属性。
- 修：新增 `NotifyClassroomQuickControlAvailabilityChanged()`，一次性发 8 个派生属性，
  上述 5 处全部改用它。

### 现象 2：一键静默更新失败后所有更新都报“已有活动维护操作”
- 事实（`%LOCALAPPDATA%\VeyonCampus\Maintenance\maintenance-runs.json`）：
  22:42:49 创建事务，22:43:07 读回 `inProgress`，之后不再推进；同时 student 健康快照报
  “当前没有未结更新事务 / Setup 1.1.86”，即学生端已放弃、版本未变，教师端却停在 `pendingVerification`。
- 根因 A：`MaintenanceJournal.Update` 的单调性规则拒绝“同一 `VerifiedStatusUtc`、事务状态却变了”的写入。
  学生端签名时间戳精度比状态机粗，`inProgress` 与随后的 `committed/rolledBack` 会拿到同一时间戳，
  于是写回被拒（历史报错“只读设备检查失败：Maintenance journal 更新不是当前操作的单调延续”）。
  修：允许 `inProgress → committed/rolledBack/notFound/needsReview/superseded` 的同时间戳推进，其余同时间戳改写仍拒绝。
- 根因 B：被学生端遗忘（`notFound`）且版本未达目标的 run 一直非终态，后续每次点击都撞
  “该设备已有活动维护操作；必须先恢复或核对原 operationId”。
  修：新增 `TeacherMaintenanceCoordinator.AbandonStaleAttemptAsync`，工作流在 resume 后识别该情形，
  标为 failed 并在同一次点击里重新 inspect + plan（`retryableDevices`）。
