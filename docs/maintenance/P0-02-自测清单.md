# P0-02：Windows 历史 Agent 与发行链自测清单

这份清单用于你在 Windows 测试机开机后自行验收。Codex 本轮没有连接 Windows 主机、运行安装器、执行 Windows 测试或对 CloudBase 做写入。当前兼容性背景与已知证据见[历史兼容性矩阵](legacy-compatibility-matrix.md)。

## 先确认测试条件

- [ ] 只用可还原的隔离测试机或虚拟机快照，不在上课用的学生机上测试更新与回滚。
- [ ] 测试对象分别是 Windows 10 和 Windows 11；记录系统版本、版本号、Build、架构。若只测其中一个，结论只覆盖该系统。
- [ ] 本轮主测试基线为 `StudentSetup 1.1.44 / Agent 0.4.56`，分别在 Windows 10 和 Windows 11 的干净快照上读回实际版本。根据用户 2026-11-03 的线上装机说明，`0.4.55` 的 `1.1.40/1.1.41` 基线暂缓；若盘点发现仍在用，再补测。
- [ ] 下载后先按[兼容矩阵](legacy-compatibility-matrix.md)里的公开 SHA-256 核对安装包，并记录来源。已检查的三份安装器没有内嵌 Authenticode 签名；Windows 可能显示未知发布者。不要把 HTTPS 或 SHA-256 结果记作 Authenticode 验收通过。
- [ ] 准备当前教师端、对应的校区签名密钥与测试发行材料。不得关闭发行验签、降低公钥检查或把 local-test 包当作 stable 包。
- [ ] 记录开始时间、快照编号、测试机名、教师端版本、安装包 SHA-256。每个失败都保留原日志与事务恢复材料，不手工清理。

## 每个快照安装后先读回基线

在管理员 PowerShell 里执行以下只读命令，将结果保存到该快照的记录中。命令不输出 Agent 配置中的私钥或完整 JSON：

```powershell
$rolePath = 'C:\Program Files\Veyon Campus\Student\veyon-campus-role.json'
$role = if (Test-Path -LiteralPath $rolePath) {
    Get-Content -LiteralPath $rolePath -Raw -Encoding UTF8 | ConvertFrom-Json
}
$os = Get-CimInstance Win32_OperatingSystem
$agent = Get-CimInstance Win32_Process | Where-Object Name -eq 'VeyonCampus.Agent.exe'
$tasks = Get-ScheduledTask -ErrorAction SilentlyContinue |
    Where-Object TaskName -like '*VeyonCampus*'

[pscustomobject]@{
    ComputerName = $env:COMPUTERNAME
    OS = $os.Caption
    OSVersion = $os.Version
    OSBuild = $os.BuildNumber
    OSArchitecture = $os.OSArchitecture
    InstalledStudentSetupVersion = $role.version
    AgentProcessCount = @($agent).Count
} | Format-List

$agent | Select-Object ProcessId, ExecutablePath, CommandLine | Format-List
foreach ($process in $agent) {
    if (Test-Path -LiteralPath $process.ExecutablePath) {
        Get-Item -LiteralPath $process.ExecutablePath |
            Select-Object FullName, Length, @{n='ProductVersion';e={$_.VersionInfo.ProductVersion}}
        Get-FileHash -LiteralPath $process.ExecutablePath -Algorithm SHA256
        Get-AuthenticodeSignature -FilePath $process.ExecutablePath |
            Select-Object Status, StatusMessage, SignerCertificate
    }
}
$tasks | Select-Object TaskName, State,
    @{n='Execute';e={$_.Actions | Select-Object -First 1 -ExpandProperty Execute}},
    @{n='Arguments';e={$_.Actions | Select-Object -First 1 -ExpandProperty Arguments}} |
    Format-List
Get-NetTCPConnection -State Listen -LocalPort 39174 -ErrorAction SilentlyContinue |
    Select-Object LocalAddress, LocalPort, OwningProcess
```

- [ ] Setup `version`、Agent 文件 `ProductVersion`、文件路径、计划任务动作和运行进程互相吻合；不吻合就先停止该快照测试并记录。
- [ ] 教师端从同一测试网络连接学生端 TCP `39174`。同时用教师端实际签名状态查询验证回执签名与设备身份；只看到端口开放不算连接验收。
- [ ] 记录教师端看到的 Agent 版本、配置指纹、健康状态和签名状态结果。对外分享日志前先脱敏设备密钥、签名、校区身份和学生信息。

## 协议与更新用例

对三个历史版本分别执行并记录。每次更新都从快照重置开始，避免上个用例留下的事务影响结果。

| 用例 | 操作 | 通过条件 | 结果 / 证据 |
| --- | --- | --- | --- |
| Windows 与二进制基线 | 记录上节读回信息；在 Win10、Win11 各覆盖目标版本 | 安装后的 Setup/Agent 版本、文件路径、任务动作与运行进程一致 | 待填写 |
| 旧 Agent 签名状态 | 用教师端向学生端请求签名状态 | 教师端验签通过，设备身份和版本读回一致；失败有明确错误且不能被记成健康 | 待填写 |
| 稳定版 Schema 3 | 从教师端推送用 Developer Release 公钥签名、SHA-256 匹配的 stable Schema 3 更新；保存教师端操作和学生 Agent 日志 | 历史 Agent 按其旧 `/v1/update` 协议完成验签、下载、暂存、切换；最终版本由签名状态回执和本机文件读回一致确认 | 待填写 |
| 不可信或被改动的稳定包 | 对隔离快照使用摘要不匹配或签名无效的测试包 | 更新被拒绝；安装文件、运行 Agent、计划任务和事务终态不发生部分切换；日志明确指出验签或摘要失败 | 待填写 |
| local-test Schema 4 | 向历史 Agent 发送仅供 local-test 使用、且不兼容其能力的 Schema 4 包 | 明确报告不支持/拒绝；不降级验签、不启动安装、不留下待切换目标 | 2026-11-03 用户截图：StudentSetup 1.1.44 / Agent 0.4.56 的签名能力回执未声明本机测试公钥，教师端在下发前拒绝；教师端门禁已观察到，学生 Agent 的 Schema 4 解析/拒绝路径未实际执行。 |
| 更新成功后健康读回 | 执行有效 stable 更新并等待交接完成 | Setup 版本、Agent 版本、运行路径、计划任务目标、配置指纹及签名健康回执都指向目标版本；事务为已提交且健康 | 待填写 |
| 失败与回滚 | 仅在可还原快照上，通过受控文件占用/测试故障触发阶段失败；按教师端现有支持的故障注入方式操作，不改生产 ACL | 回滚读回旧 Setup/Agent、旧任务动作和旧配置指纹；旧版 Agent 健康。若进入 `recoveryRequired`，保留材料并记失败，不能算回滚通过 | 待填写 |
| `1.1.40` 旧指纹迁移 | 从 1.1.40 干净快照执行有效更新，再在隔离快照触发可回滚失败 | 正常迁移后新指纹一致；失败回滚后恢复旧指纹；两种情况均有签名状态读回 | 待填写 |
| 旧 Setup 版本别名目录 | 使用包含历史 Setup 版本别名目录布局的受控快照执行更新与回滚 | 正确识别别名，不误删、不覆盖无关目录；恢复后旧 Agent 可启动并通过签名健康检查 | 待填写 |

如果教师端没有 Schema 3 stable 包、没有可用的 Developer Release 公钥，或其请求走到未部署的 v4 路由，就把用例记为 **BLOCKED**，不要拿 production 当前发行响应替代测试发行材料。production 目前 `/v4/releases/latest` 为 404，且没有 Agent target sidecar。

## CloudBase 发行链（仅隔离测试环境）

当前仓库只配置 production CloudBase 环境，production 尚无本次 v4 路由和两条目标 migration。不要在 production 做此项自测。先由你提供/配置独立测试环境及发行公钥，并将测试环境准备到部署脚本列出的既有 migration 基线；allowlist helper 会检查该基线，不满足就停止。然后再在该环境验证：

先可运行 helper 的**离线契约测试**；它使用假的 CloudBase CLI，不连接 CloudBase，也不应用 SQL：

```bash
node --test scripts/apply-cloudbase-release-migrations.test.cjs
```

仓库新增的 [allowlist migration helper](../../scripts/apply-cloudbase-release-migrations.sh) 只把两条目标 SQL 放进临时配置目录，默认只预演；它先核对 API 所需的远端基线 migration，拒绝缺失基线或已含禁用 OperationsReporting migration 的环境，并拒绝仓库 production envId。登录 CloudBase CLI 后，先替换为你确认可隔离、可恢复的测试环境 ID：

```bash
TEST_ENV_ID='替换为隔离测试环境ID'
bash scripts/apply-cloudbase-release-migrations.sh \
  --env-id "$TEST_ENV_ID" \
  --confirm-isolated-env "$TEST_ENV_ID" \
  --dry-run
```

检查基线核对信息及 JSON 中的环境 ID、pending 列表和无冲突结果都正确后，才可在隔离环境应用。应用命令需要再次显式输入同一环境 ID 和完整 migration ID 清单：

```bash
bash scripts/apply-cloudbase-release-migrations.sh \
  --env-id "$TEST_ENV_ID" \
  --confirm-isolated-env "$TEST_ENV_ID" \
  --apply \
  --confirm-migration-ids 20261021140000,20261102120000
```

不要对 production 运行应用模式，也不要用通用 `--include-all` 代替该 allowlist。

- [ ] migration ledger 显示 `20261021140000_create_file_update_release_catalog` 与 `20261102120000_support_signed_student_agent_targets` 已按受支持顺序应用。
- [ ] 部署后的 `/v4/releases/latest?role=StudentSetup&architecture=win-x64` 返回预期正式发行；响应签名可由教师端验证。
- [ ] Agent target sidecar 的签名、版本和安装器 SHA-256 绑定关系通过教师端验证；改动响应、签名、摘要或版本后必须拒绝。
- [ ] 旧 `/v3/releases/latest` 仍按兼容约定返回 Schema 3；验证它不会把缺失 Agent target 当作当前 Agent 版本。
- [ ] 从测试环境实际下载发行包并复算 SHA-256，与签名 manifest 相符；记录环境 ID、API 响应、部署版本及日志关联 ID，隐藏密钥。
- [ ] 在测试环境清理或回滚方案明确后，才开始任何 migration/API 联合部署验证。

2026-11-03 的只读 migration 预演确认两条目标 migration 待应用，并报告已禁用的旧 `20261010090000_add_daily_operations_reporting` 顺序冲突。CloudBase CLI 3.8.5 有 `--include-all` 越序选项，但当前没有证据确认它只会应用目标迁移；仓库部署脚本明确排除了这条旧迁移。新增的 allowlist helper 未运行，只有你确认隔离测试环境并按上面的顺序先预演，再决定是否应用。不要在 production 运行应用模式，也不要用通用 `--include-all` 代替 allowlist。
