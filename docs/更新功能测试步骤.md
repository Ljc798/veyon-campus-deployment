## GitHub Actions 自动构建

学生端顶部的“软件更新”已移到“管理员维护 → 更新学生部署工具…”，供单机维护与离线更新使用。日常在教师端“学生端静默更新”中推送 StudentSetup 安装包，由学生 Agent 执行安装并在需要时切换 Agent。批量更新包括部署工具和后台 Agent；独立入口保留的是单机维护方式，不要求逐台手动更新。

推送分支代码或创建 PR 后，`Windows installers` 工作流运行 API 和 .NET 检查、构建 Student 与 Teacher 两个 Inno Setup 安装器，并执行安装/卸载冒烟测试。成功后会上传仅含 EXE 的 `windows-installers-<run id>` Actions artifact，保留 14 天。

稳定 tag 构建会先把仓库公钥变量写入 runner 临时文件，再运行 .NET 检查；检查将嵌入公钥的 SPKI 指纹与该文件比对。Windows 打包脚本还会逐个核对 Teacher/Student 发布目录中的 Core 程序集是否嵌入了相同 PEM 字节，并运行单文件更新助手的只读诊断入口核对其指纹。普通分支构建则验证应用程序集没有发行公钥，且更新助手按设计失败关闭。本机已用临时 RSA 测试密钥验证了无公钥、带公钥及错误指纹三条路径；Windows PowerShell 打包脚本和 Inno Setup 行为仍须由 Windows Actions runner 验收。

推送稳定版本 tag（例如 `v0.4.55`）会额外启动正式发布任务。tag 必须与 `VeyonCampus.App.csproj` 中的版本一致。工作流会使用固定 Developer Release 公钥构建两种安装器，先把同一批 EXE 与 `SHA256SUMS` 发布到 GitHub Release 和 Gitee Release，下载校验附件后，再将 RSA-PSS 签名元数据写入 CloudBase。发布时会把 GitHub 上的精确版本 tag 推送到 Gitee，因此 Gitee Release 的源码 tag 指向同一提交。应用内更新继续查询 CloudBase API，安装包从配置的 GitHub/Gitee Release 下载。

发布任务使用 GitHub Environment `production-release`。运行前需要配置：

- Repository variable：`VEYONCAMPUS_RELEASE_PUBLIC_KEY_PEM`、`GITEE_OWNER`、`GITEE_REPO`、`GITEE_USERNAME`。
- `production-release` environment secrets：`VEYONCAMPUS_RELEASE_PRIVATE_KEY_PEM`、可选口令 `VEYONCAMPUS_RELEASE_PRIVATE_KEY_PASSPHRASE`、`CLOUDBASE_ENV_ID`、`CLOUDBASE_API_KEY`、`CLOUDBASE_SERVICE_ROLE_KEY_ROTATED_AFTER_20260930_REVIEW=yes`、`GITEE_TOKEN`。
- CloudBase 私钥与 Developer Release 私钥必须分别使用。Gitee token 需要同时支持目标仓库 HTTPS 推送 tag、通过 V5 API 创建 Release 和上传附件；`GITEE_USERNAME` 是该 token 对应的 Gitee 登录名。Gitee 仓库需预先存在。

CloudBase 发布脚本会检查公私钥配对、当前 latest 版本和 SHA-256；同版本同文件可安全重跑，改过字节的同版本会拒绝。Gitee 发布脚本先核对 `SHA256SUMS`，重试时验证已存在附件；上传新附件后再经下载接口取回每个文件并比对 SHA-256。上传中断后只续传缺失附件，不会混用不同构建。API 端点和附件操作参见 [Gitee OpenAPI V5 仓库 Release 接口](https://gitee.com/sdk/gitee5j/blob/main/docs/RepositoriesApi.md)。

当前仓库还没有配置生产密钥、Gitee 仓库路径或 Actions 发布凭据。因此生产 tag 目前会在发布预检阶段停止；先完成密钥、变量和环境配置，再用可回滚的 Windows VM 验收首个正式版本。非 tag 的 Actions artifacts 没有生产公钥，不用于应用内更新测试。

## TeacherConsole 离线更新包转移

联网教师端与断网目标机需分别使用**已安装且已信任的 TeacherConsole** 操作。联网端应运行嵌入与该 Release 匹配的固定 Developer Release 公钥的版本，并连接到提供该签名 Release 的同一 CloudBase API。

1. 在“更新”页检查 TeacherConsole 更新；发现高于当前版本的签名 Release 后，点击“导出离线更新包”，选中学校批准的加密介质目录。
2. 确认导出目录同时包含 `VeyonCampus-Teacher-Setup-<version>-win-x64.exe` 和同名 `.release.json`。不要改名、拆开或覆盖其他版本；安全移除介质前等待导出完成。
3. 在断网目标机从 `Program Files` 启动此前已安装的 TeacherConsole，进入“更新 → 离线安装器验证”，选中介质上的 EXE。程序会验固定公钥签名及目标角色/版本、API 来源、文件名、大小和 SHA-256，并把再次验证过的副本存入 `%LOCALAPPDATA%\VeyonCampus\Updates`。
4. 核对界面显示的版本与 SHA-256，再点击“安装已验证版本并重启”。更新助手会再次验签、请求 UAC、验证安装结果，并在失败时尝试恢复原安装。安装后按下方 Windows VM 验收步骤记录版本读回和恢复证据。

TeacherConsole 的导出、离线验证和安装过程仍需在 Windows VM 验收；没有匹配生产公钥的受信任旧版时，不要把测试签名包当成正式离线更新。

## StudentSetup 在线与离线自更新

StudentSetup“管理员维护 → 更新学生部署工具…”打开更新窗口后会查询 CloudBase 的 StudentSetup latest-release；可以手动再次检查、下载并重启，或导出离线包。只有嵌入对应 Developer Release 公钥的安装版本才会接受在线或离线更新。

1. 联网时点击“下载并重启”。StudentSetup 会检查角色、版本、签名、安装器长度和 SHA-256，将安装器与 `.release.json` 放入 `%LOCALAPPDATA%\VeyonCampus\Updates`，再启动固定目录中的更新助手。
2. 若需转移到断网电脑，点击“导出离线更新包…”，选择学校批准的加密介质目录。完成后确认目录同时包含 `VeyonCampus-Student-Setup-<version>-win-x64.exe` 与同名 `.release.json`；不要拆开、改名或覆盖其他版本。
3. 断网电脑从 `Program Files` 启动 StudentSetup，进入“软件更新”，选择介质上的 EXE。程序会使用内嵌公钥验证发布清单和安装器，将副本安全暂存后，显示版本与 SHA-256。
4. 确认版本后点击“安装已验证版本并重启”。更新助手会再次验签并请求 UAC；安装失败或版本回读不符时会尝试恢复旧版本。在线下载、离线转移、UAC、成功读回和失败回滚均待 Windows VM 验收。

```powershell
$env:VEYONCAMPUS_DEPLOYMENT_PACKAGES_API_BASE_URL = 'https://<测试环境函数根地址>/'

Start-Process (Join-Path $env:ProgramFiles 'Veyon Campus\Teacher\VeyonCampus.Teacher.exe')
```

发布脚本的 `cloudbaserc.json`、`CloudBase__EnvId` 和测试 VM 的 API 地址都应指向同一环境。只设置发布脚本的环境变量不会自动切换客户端查询地址。用进程级变量仅影响从这个 PowerShell 启动的测试程序，不会永久改动 VM 系统环境。

## 虚拟机验收

1. VM 保持安装旧的 `0.4.47` 测试教师端，且在当日尚未成功发送 Teacher 心跳时启动，或直接使用“更新”页里的手动检查。
2. 发布环境中存在更高版本的已签名 Teacher 清单后，点击“检查更新”。应弹窗显示角色、当前版本和最新版本；关闭提示后不应自动下载或安装。
3. 若要继续测下载与安装，先还原 VM 快照，手动确认下载；验证清单签名、文件大小和 SHA-256 通过、重启后版本读回为新版本。
4. 把安装包或清单改动一个字节，或用错误私钥签名，客户端都应拒绝该版本。
5. 学生端更新是独立的 `StudentSetup` 角色。需分别构建并发布同一更高版本的 Student 安装包，再在可还原的学生测试 VM 验证；不要用真实机房首次测试。

日常心跳会携带 TeacherConsole 和 StudentSetup 的最新签名版本；客户端完成验签和版本比较后只显示提醒，不会自行下载或安装。验证心跳提醒时，使用尚未成功发送当日心跳的快照，避免 UTC+8 去重跳过本次请求。

## 正式版发布流程与手工兜底

正常流程是在隔离环境完成更新验收后，先确认上述环境变量和 Secrets 已齐备，再将与 App 项目版本相同的 `vX.Y.Z` tag 推送到 GitHub。`Windows installers` 工作流会生成 CloudBase 签名清单并创建 GitHub/Gitee 同版本 Release。应用更新查询 CloudBase API，再由 artifact 入口跳转到 GitHub/Gitee 下载安装包；不自动跨站回退。

安装包文件名保持版本化且一致，例如：

```text
VeyonCampus-Teacher-Setup-0.4.54-win-x64.exe
VeyonCampus-Student-Setup-0.4.54-win-x64.exe
```

若 Actions 发布凭据暂时不可用，需要手工发布时，先在 GitHub 与 `https://gitee.com/<GITEE_OWNER>/<GITEE_REPO>/releases` 创建同名 `vX.Y.Z` Release 并附上两种安装器与 `SHA256SUMS`，核对附件后再运行 `publish-application-release.cjs` 将 TeacherConsole 和 StudentSetup 的签名元数据写入 CloudBase。脚本会重新下载所选外部源安装包核对摘要，不上传 EXE 到 CloudBase。Gitee 仓库必须包含同一提交/tag。

发布后分别从 GitHub 和 Gitee 下载各一份安装器，核对文件名及 SHA-256 与本地构建文件一致。测试版不放到这两个公开仓库；正式公开前再上传，避免用户下载到测试密钥签名的版本。

本仓库的 Windows workflow 已具备上述 tag 发布路径；运行前仍需把 `<GITEE_OWNER>` 和 `<GITEE_REPO>` 定为仓库变量并配置 `production-release` Environment。测试 Release 私钥绝不能配置到生产 Environment，也不得把测试版本推成公开 `vX.Y.Z` tag。

## 不打开网页直接下载 Gitee Release

公开仓库可以直接用发行版附件地址下载，不用打开 Gitee 网页：

```powershell
$url = 'https://gitee.com/<GITEE_OWNER>/<GITEE_REPO>/releases/download/v0.4.54/VeyonCampus-Teacher-Setup-0.4.54-win-x64.exe'
Invoke-WebRequest -Uri $url -OutFile '.\VeyonCampus-Teacher-Setup-0.4.54-win-x64.exe'
```

公开仓库的直链格式为 `https://gitee.com/<owner>/<repo>/releases/download/<tag>/<文件名>`。私有仓库或自动化程序可调用 Gitee V5 API：先用 `GET /api/v5/repos/{owner}/{repo}/releases/tags/{tag}` 按 tag 读取 Release，再用 `GET /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files` 列出附件，最后请求 `GET /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files/{attach_file_id}/download`。API 下载端点返回二进制文件；需要 OAuth Bearer Token 时放在请求头，不要写进 URL 或日志。下载后仍应比对 SHA-256。
