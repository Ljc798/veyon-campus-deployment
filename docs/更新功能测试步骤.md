# Developer Release 更新测试步骤

当前项目版本是 `0.4.45`。客户端只有在构建时嵌入 Developer Release **公钥**，才能验证版本清单；当前已安装的客户端若没有该公钥，更新检查不可用。测试公钥位于：

应用内更新当前以 **CloudBase 为唯一正式更新源**：签名清单和安装包由 `veyon-api` 提供。GitHub Releases 与 Gitee Releases 保存同一批带版本号的安装包，方便用户查看和手动下载；它们是公开分发镜像，应用内更新不会自动切换到这两个站点。测试版只发到隔离的 CloudBase 测试环境，不要上传到公开的 GitHub/Gitee Release。

```text
%LOCALAPPDATA%\VeyonCampus\ReleaseKeys\Test\release-public.pem
```

私钥和口令仅用于发布清单，绝不能放进 Git、安装包或 CloudBase 客户端配置。测试密钥只用于测试环境，正式发布需使用另一套生产密钥。

## GitHub Actions 自动构建

推送代码或创建 PR 后，`Windows installers` 工作流会运行 API 和 .NET 检查、构建 Student 与 Teacher 两个 Inno Setup 安装器，并执行安装/卸载冒烟测试。成功后会上传名为 `windows-installers-<run id>` 的 Actions artifact，保留 14 天，可从对应的 Actions 运行页面下载。

这个工作流只生成临时测试产物，不会创建 GitHub Release，也不会把附件同步到 Gitee。它没有传入 Developer Release 公钥，因此 Actions 产出的安装器不能用于带签名清单的应用内更新测试；请按本页步骤用测试公钥单独构建旧版和新版，再把新版发布到隔离的 CloudBase 测试环境。

## 先准备旧版本测试机

先用带测试公钥的 `0.4.45` 教师安装包覆盖安装到可还原的虚拟机。这样更新检查页才有能力校验后续发布的测试版本：

```powershell
$publicKey = Join-Path $env:LOCALAPPDATA 'VeyonCampus\ReleaseKeys\Test\release-public.pem'
.\scripts\package-windows-offline.ps1 `
  -Role TeacherConsole `
  -ReleasePublicKeyPath $publicKey `
  -OutputDirectory 'artifacts\update-test\teacher-0.4.45' `
  -InstallerPath 'artifacts\update-test\VeyonCampus-Teacher-Setup-0.4.45-win-x64.exe'
```

确认输出安装包成功，再安装到测试 VM。启动后进入教师端“更新”页，确认没有“缺少公钥”错误；此时可以先点“检查更新”。若版本目录尚无发布记录，页面会显示“目前没有已发布的教师控制台版本”；只有目录中已有签名版本时，才会显示云端版本和“当前已是最新版本”。

## 准备更高版本

在隔离的测试分支或工作区，将 `src/VeyonCampus.App/VeyonCampus.App.csproj` 的版本从 `0.4.45` 临时递增到更高版本（例如 `0.4.46`），再用**同一测试公钥**构建教师端：

```powershell
.\scripts\package-windows-offline.ps1 `
  -Role TeacherConsole `
  -ReleasePublicKeyPath $publicKey `
  -OutputDirectory 'artifacts\update-test\teacher-0.4.46' `
  -InstallerPath 'artifacts\update-test\VeyonCampus-Teacher-Setup-0.4.46-win-x64.exe'
```

新版本安装包必须与发布清单的角色、版本一致。发布脚本会计算安装包 SHA-256，用测试私钥签名清单并上传安装包。发布前它会检查私钥和公钥是否匹配。发布脚本要求的环境变量为：

```text
CloudBase__EnvId
CloudBase__ApiKey
VEYONCAMPUS_RELEASE_PRIVATE_KEY_PATH
VEYONCAMPUS_RELEASE_PUBLIC_KEY_PATH
VEYONCAMPUS_RELEASE_PRIVATE_KEY_PASSPHRASE
CLOUDBASE_SERVICE_ROLE_KEY_ROTATED_AFTER_20260930_REVIEW=yes
```

在发布环境和上述值确认后，执行：

```powershell
node .\scripts\publish-application-release.cjs `
  --role TeacherConsole `
  --version 0.4.46 `
  --installer .\artifacts\update-test\VeyonCampus-Teacher-Setup-0.4.46-win-x64.exe `
  --confirm-publication
```

**发布会把可查询的版本和安装包写入 CloudBase，具有外部可见效果。** 本仓库目前的 `cloudbaserc.json` 指向共用环境，版本记录按角色、架构和版本唯一；不要为了弹窗测试就把临时版本发到共用环境。先准备隔离的 CloudBase 测试环境并让发布脚本指向它，或确认该版本号就是准备公开发布的版本。当前没有在本步骤代替你发布任何版本。

隔离环境需先应用数据库迁移并部署 `veyon-api`，再让测试 VM 查询对应 API。测试进程可通过 `VEYONCAMPUS_DEPLOYMENT_PACKAGES_API_BASE_URL` 指定该环境的 HTTPS 函数根地址，并通过 `VEYONCAMPUS_CLOUDBASE_ENV_ID` 指定环境 ID；在测试 VM 的 PowerShell 中临时设置这两个变量，再从同一窗口启动教师端：

```powershell
$env:VEYONCAMPUS_DEPLOYMENT_PACKAGES_API_BASE_URL = 'https://<测试环境函数根地址>/'
$env:VEYONCAMPUS_CLOUDBASE_ENV_ID = '<测试环境 ID>'
Start-Process (Join-Path $env:ProgramFiles 'Veyon Campus\Teacher\VeyonCampus.Teacher.exe')
```

发布脚本的 `cloudbaserc.json`、`CloudBase__EnvId` 和测试 VM 的 API 地址都应指向同一环境。只设置发布脚本的环境变量不会自动切换客户端查询地址。用进程级变量仅影响从这个 PowerShell 启动的测试程序，不会永久改动 VM 系统环境。

## 虚拟机验收

1. VM 保持安装旧的 `0.4.45` 测试教师端，且在当日尚未成功发送 Teacher 心跳时启动，或直接使用“更新”页里的手动检查。
2. 发布环境中存在更高版本的已签名 Teacher 清单后，点击“检查更新”。应弹窗显示角色、当前版本和最新版本；关闭提示后不应自动下载或安装。
3. 若要继续测下载与安装，先还原 VM 快照，手动确认下载；验证清单签名、文件大小和 SHA-256 通过、重启后版本读回为新版本。
4. 把安装包或清单改动一个字节，或用错误私钥签名，客户端都应拒绝该版本。
5. 学生端更新是独立的 `StudentSetup` 角色。需分别构建并发布同一更高版本的 Student 安装包，再在可还原的学生测试 VM 验证；不要用真实机房首次测试。

日常心跳会携带 TeacherConsole 和 StudentSetup 的最新签名版本；客户端完成验签和版本比较后只显示提醒，不会自行下载或安装。验证心跳提醒时，使用尚未成功发送当日心跳的快照，避免 UTC+8 去重跳过本次请求。

## 正式版上传到 GitHub 和 Gitee

先在隔离环境完成上面的更新验收，再用生产 Release 私钥和生产 CloudBase 环境发布。CloudBase 成功后，把同一版的两个 Inno Setup 安装器作为 GitHub 与 Gitee 上同名 Release 的附件。Gitee 仓库路径采用 `owner/repo`；路径确定后，把下面的 `<GITEE_OWNER>` 和 `<GITEE_REPO>` 替换成实际值。

安装包文件名保持版本化且一致，例如：

```text
VeyonCampus-Teacher-Setup-0.4.46-win-x64.exe
VeyonCampus-Student-Setup-0.4.46-win-x64.exe
```

GitHub：打开代码仓库的 **Releases → Draft a new release**，选择或创建 `v0.4.46` 标签，把两个安装器拖入附件，填写版本说明并发布。Gitee：打开 `https://gitee.com/<GITEE_OWNER>/<GITEE_REPO>/releases`，为同一提交创建相同标签的 Release，再附上同一批安装器。若 Gitee 是代码镜像，先确认对应 tag 已同步到 Gitee。

发布后分别从 GitHub 和 Gitee 下载各一份安装器，核对文件名及 SHA-256 与本地构建文件一致。测试版不放到这两个公开仓库；正式公开前再上传，避免用户下载到测试密钥签名的版本。

如果希望由 GitHub Actions 自动生成签名清单并同步附件，还需要先确定 Gitee `owner/repo`，再为 GitHub 配置隔离的 test/production environment、对应 CloudBase 凭据、环境对应的 Release 私钥和口令，以及 Gitee Access Token。公钥可以作为环境变量，私钥只能作为受保护的 Secret；目前本仓库尚未配置 Gitee 仓库路径或这些 Actions 凭据。

## 不打开网页直接下载 Gitee Release

公开仓库可以直接用发行版附件地址下载，不用打开 Gitee 网页：

```powershell
$url = 'https://gitee.com/<GITEE_OWNER>/<GITEE_REPO>/releases/download/v0.4.46/VeyonCampus-Teacher-Setup-0.4.46-win-x64.exe'
Invoke-WebRequest -Uri $url -OutFile '.\VeyonCampus-Teacher-Setup-0.4.46-win-x64.exe'
```

公开仓库的直链格式为 `https://gitee.com/<owner>/<repo>/releases/download/<tag>/<文件名>`。私有仓库或自动化程序可调用 Gitee V5 API：先用 `GET /api/v5/repos/{owner}/{repo}/releases/tags/{tag}` 按 tag 读取 Release，再用 `GET /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files` 列出附件，最后请求 `GET /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files/{attach_file_id}/download`。API 下载端点返回二进制文件；需要 OAuth Bearer Token 时放在请求头，不要写进 URL 或日志。下载后仍应比对 SHA-256。
