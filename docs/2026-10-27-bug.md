# Veyon Campus 稳定性修复与 UI 整改任务书

**任务类型：** Bug Fix / Reliability / UI Refactoring  
**目标平台：** Windows / C# / Avalonia  
**优先级：** P0 → P1 → P2  
**适用范围：** 教师端、学生 Agent、更新器、课堂策略模块

## 一、总体目标

目前 Veyon Campus 已经在真实校区环境中使用，但在约 18 台学生电脑的场景下，出现了后台任务阻塞、策略执行不稳定、升级状态异常以及 UI 布局失控等问题。

本次整改以稳定性优先，不进行无必要的大规模重写。

核心原则：

1. 教师端不应因学生机离线或任务超时而卡顿。
2. 所有远程操作必须有明确的开始、完成、失败或待同步状态。
3. 课堂策略使用期望状态与实际状态分离的架构。
4. 界面布局不得随数据量增长而无限扩展。
5. 保持现有 Veyon 监控、Agent 通信、升级及安全验证功能。
6. 必须兼容现有部署环境和可支持的旧版本。

## 二、P0：核心功能与稳定性

### BUG-01：旧版本清理与原子恢复失败

**现场错误：**

- 配置清理未完成。
- `PreviousSetupPreserved` 遗留安全恢复任务异常。
- 旧版本文件或配置无法完成恢复。

**排查任务：**

- 搜索 `PreviousSetupPreserved` 的定义及调用链。
- 通过 Git 历史确定首次引入版本及相关修复提交。
- 排查 ACL、文件占用、服务停止、回滚文件缺失等问题。
- 检查升级失败后的持久化事务状态。
- 检查不同版本间升级恢复协议的兼容性。

**整改要求：**

- 升级事务必须支持崩溃恢复和安全重试。
- 恢复任务具有幂等性。
- 成功恢复后清理遗留事务记录。
- 未确认恢复成功前不得删除必要的备份。
- 明确区分安装失败、恢复失败和需要人工处理。

**验收：** 升级中断、重启、恢复失败再重试时，不丢失学生端必要配置及身份信息。

### BUG-02：学生端更新结果核对卡住

**现场表现：**

- 多台电脑长期显示「正在核对更新结果」。
- 显示「已接收 64.5 MB，等待安装程序完成」。
- 出现 `UPDATE_INPUT_INVALID`。
- 用户无法明确知道更新是否完成。

**整改要求：**

1. 安装前校验完整更新包、格式、适用目标及完整性。
2. 区分文件接收、校验、安装、重启 Agent、版本确认等阶段。
3. 各阶段设置独立的合理超时。
4. 不得仅依据文件接收进度推断安装成功。
5. 安装器退出后必须记录退出码及最终状态。
6. 教师端可以重新连接并查询更新结果。
7. 超时后进入明确的未知或失败状态，不无限显示「核对中」。
8. 安装失败时保留诊断信息与安全恢复入口。

**验收：** 即使学生 Agent 崩溃、断网或更新失败，教师端也可以结束本次等待并展示准确的可确认结果。

### BUG-03：课堂策略提前解除与执行卡顿

**现场表现：**

- 18 台电脑执行网站限制时明显卡顿。
- 部分策略尚未执行完成就进入恢复阶段。
- 状态出现「需核对」「恢复中」，但没有可靠完成回执。
- 教师端切换其他页面仍然卡顿。

**重点排查：**

- 自动解除计时器是否与策略下发竞争。
- 旧课堂任务是否覆盖新的策略任务。
- 是否存在主线程同步等待、共享锁竞争、无界并发。
- 是否重复创建连接、轮询或恢复任务。
- 是否把离线设备的持续超时当作执行中的任务。

**整改要求：**

1. 引入 `DesiredState`、`ActualState`、`PolicyRevision`。
2. 同一学生机的冲突策略写操作必须有序执行。
3. 不同学生机可以有界并发。
4. 旧版本策略不得覆盖新版本。
5. 使用异步后台任务，不阻塞 Avalonia UI。
6. 任务取消、失败、重试、超时必须有明确规则。
7. UI 状态更新进行合并与节流。
8. 禁止多个页面重复创建相同的后台协调任务。

**验收：** 18 台电脑批量应用与解除策略时，教师端能够正常切换页面、滚动和操作，策略不会被过期任务错误覆盖。

### BUG-04：离线学生机无限等待恢复

**现场表现：**

- 部分学生机已经关机。
- 教师端依然显示「正在恢复」。
- 长时间重复请求造成全局卡顿。

**整改要求：**

学生机状态应至少区分：

- 已同步
- 执行中
- 离线待同步
- 待核对
- 执行失败
- 需要人工处理

设备离线后，不应继续高频发送恢复请求。

改为：

1. 在线状态由统一心跳或连接管理器维护。
2. 离线后停止当前无意义的网络重试。
3. 持久化最新的待同步期望状态。
4. 学生 Agent 重新上线时自动同步最新策略。
5. 学生端应能依据可信的本地到期信息恢复临时管控。
6. 离线或恢复失败不能阻塞整个课堂或其他设备操作。
7. 教师端重启后能够恢复未完成操作的准确状态。

**验收：** 18 台电脑中即使 13 台离线，教师端仍然保持可操作，且不会持续占用大量资源重复请求离线设备。

## 三、P1：课堂生命周期设计

### FEATURE-01：自动管理课堂开启与关闭

当前课堂状态管理需要明确化。

**默认状态：课堂已关闭。**

预期逻辑：

- 开启第一项课堂管控策略 → 自动进入「课堂运行中」。
- 继续启用其他可兼容的策略 → 保持运行中。
- 关闭部分策略 → 只解除对应策略。
- 所有策略关闭或到期 → 自动进入「课堂已关闭」。
- 学生机断线或关机 → 不改变课堂整体状态。
- 课堂关闭后 → 不再下发旧的限制策略。

课堂会话状态和学生设备的执行状态必须分离。

建议维护：

```text
Classroom
  DesiredPolicies
  ClassroomRevision
  LifecycleState
  ExpirationTime

StudentDevice
  ConnectionState
  DesiredPolicyRevision
  AppliedPolicyRevision
  LastAcknowledgement
  LastSeen
  PendingOperation
```

上述结构仅供架构参考，应优先复用现有服务和实体。

**重要限制：**

- 课堂关闭不应停止设备监控、心跳和 Agent 通信。
- 教师端关闭不代表所有离线设备已执行恢复。
- 必须防止旧恢复任务解除新课堂的管控。
- 必须解决教师端重启、策略到期、学生端断网之间的竞态条件。
- 对键鼠限制等可能影响操作安全的功能，应提供独立的超时解除及应急恢复机制。

## 四、P1：UI 布局与交互整改

### BUG-05：网站黑名单过长导致弹窗无法关闭

**现场表现：**

- 黑名单有大量域名。
- 确认弹窗超出屏幕高度。
- 文本换行混乱。
- 关闭按钮不可见或难以操作。
- 滚动和交互异常。

**整改要求：**

1. 弹窗使用受视口限制的最大高度和宽度。
2. 长内容放进独立 `ScrollViewer`。
3. 默认只显示策略摘要，例如域名数量、模式、设备数量与截止时间。
4. 完整域名清单通过折叠区域查看。
5. 支持搜索域名。
6. 长域名正确换行或省略，并可查看完整内容。
7. Escape、取消、关闭按钮始终可用。
8. 弹窗不因数据长度增加而突破屏幕边界。
9. 大量域名采用合适的虚拟化或增量渲染方案，避免一次性生成过多视觉元素。

**验收：** 100、500、1000 个域名下均能正常打开、滚动、确认和关闭。

### BUG-06：学生电脑详情页面样式混乱

**现场表现：**

- 展开设备详情后出现大面积无效留白。
- 「未读取」等状态重复展示，但没有字段名称。
- 诊断信息缺少层级与分组。
- SHA-256 指纹直接显示一整行，破坏布局。
- 状态标签、正文和警告混在一起。
- 页面存在嵌套滚动区域，操作体验不佳。
- 需要教师核对的身份问题缺少明显、准确的操作入口。

**整改方向：**

#### 1. 设备列表保持简洁

默认只展示：

- 学生姓名 / 设备编号
- 在线状态
- Agent 连接状态
- 策略同步状态
- 是否需要人工处理

不要在列表中展示长诊断日志。

#### 2. 展开详情使用分组布局

建议分为：

**设备信息**
- 学生姓名
- 设备编号
- 最后在线时间
- Agent 版本

**策略状态**
- 网站限制
- 键鼠限制
- 期望版本 / 已应用版本
- 最后回执时间

**安全与身份**
- Agent 签名校验结果
- 身份绑定状态
- 已绑定指纹
- 当前提交指纹
- 核对或重新绑定操作

**诊断信息**
- 最近一次错误
- 错误代码
- 详细日志
- 复制诊断信息

#### 3. 优化状态文案

禁止无标签地重复显示「未读取」。

例如：

```text
网站策略：尚未读取
键鼠状态：尚未读取
最后回执：无可用记录
身份绑定：等待教师核对
```

对于字段缺失，应区分「尚未获取」「设备离线」「读取失败」「不支持」等不同原因。

#### 4. 长字符串处理

对于 Agent 指纹：

- 默认展示缩略形式。
- 提供复制完整指纹的按钮。
- 可在详情中查看完整值。
- 不允许长字符串撑破容器。
- 核对时仍应使用完整指纹，不能依据缩略值判断身份一致。

#### 5. 安全状态操作

对于「Agent 签名有效但身份尚未固定」：

- 保留安全警告。
- 显示原因。
- 提供明确的人工核对入口。
- 教师确认前不得自动信任未知身份。
- 禁止为了消除提示而绕过原有安全机制。

#### 6. 滚动与列表优化

- 优先保留页面单层主滚动。
- 展开区高度随必要内容合理调整。
- 长日志使用有界滚动区域。
- 设备列表超过一定数量时使用虚拟化。
- 展开某台设备不能导致整个页面明显卡顿。
- 翻页后设备状态与展开状态应符合预期。

**验收：** 展开任意设备时，页面整洁、信息可读，长指纹不破坏布局，操作入口明确。

## 五、技术实现约束

当前项目采用 C# + Avalonia，整改时遵循以下要求：

1. 优先修复 ViewModel、后台服务、状态模型和异步调度。
2. UI 组件优先保持现有设计系统一致，可评估使用 SukiUI，但不要为单个界面随意引入多个 UI 框架。
3. 不因 UI 整改显著增加安装包体积。
4. 禁止在 UI 线程执行网络 IO、文件 IO、同步等待或大量策略计算。
5. 尽量复用现有日志、Agent 协议及更新机制。
6. 涉及协议和持久化格式变更时，必须考虑旧学生端兼容。
7. 不允许未经验证就自动修改学生机身份信任关系。
8. 不允许通过简单延长超时时间掩盖死锁、无限重试或状态机错误。

## 六、测试与验收

### 并发性能测试

测试 1、5、18、30、60 台设备。

覆盖：

- 全部在线
- 部分离线
- 全部离线
- 下发过程中突然关机
- 重新上线
- 快速开启及解除策略
- 教师端跨页面操作
- 批量更新与策略执行的资源竞争

记录每阶段耗时、任务数量、CPU、内存、UI 响应延迟及失败率。

### UI 测试

覆盖：

- 100–1000 个域名的黑名单
- 不同 Windows 缩放比例
- 小屏幕、低分辨率及窗口缩放
- 长设备名称和长错误消息
- 长指纹和大量日志
- 18–70 台设备列表
- 弹窗、分页、展开、滚动与关闭操作

### 故障恢复测试

覆盖：

- 更新中断
- Agent 崩溃
- TCP 连接超时
- 策略下发中断
- 教师机重启
- 学生机重启
- 身份未绑定
- 旧版本 Agent 接入
- 离线时课堂策略过期

## 七、执行顺序

请按以下顺序执行，不要同时大规模改动多个模块。

**第一阶段：代码审查**

查找上述问题对应的代码位置、调用链、并发机制及相关 Git 提交。

输出：

- 直接证据
- 已确认根因
- 尚未确认的假设
- 受影响版本
- 修复方案
- 风险与兼容性影响

不要把截图现象直接当作已经确认的代码根因。

**第二阶段：P0 修复**

优先修复课堂策略提前解除、离线无限恢复、后台卡顿、更新状态卡住和原子恢复异常。

**第三阶段：架构整理**

实现明确的课堂生命周期、期望状态协调、离线待同步及安全的策略版本管理。

**第四阶段：UI 整改**

修复网站名单弹窗、学生设备详情以及相关滚动、排版、状态文案问题。

**第五阶段：回归测试**

尽可能编写自动化测试；无法在当前环境执行的硬件或多机测试，应提供可复现的测试步骤，不得虚报通过。

请先完成代码审查和根因定位，再按优先级实施修复。避免大规模重写，优先采用能够验证的最小必要改动。
