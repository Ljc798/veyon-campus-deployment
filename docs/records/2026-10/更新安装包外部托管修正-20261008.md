# 更新安装包外部托管修正

用户明确要求安装包使用 CloudBase 以外的托管，避免消耗 CloudBase 安装器存储和下载流量。当时将 GitHub 和另一国内镜像作为手动下载源，应用更新仍跳转到 CloudBase 私有桶；本轮修正了该实现和操作文档。当前应用更新统一使用 GitHub，GitCode 仅计划作为手动 ZIP 镜像。

## 当前流程

1. 构建两种角色的安装包和 SHA256SUMS，发布 GitHub Release，并同步当时的国内镜像 Release。
2. 验证外部附件与构建字节相同，生成 Developer Release 签名清单，只向 CloudBase 写入版本、大小、摘要、签名及兼容能力等 JSON 元数据。所选外部源附件不可用或摘要不符时不写入新版本。
3. 客户端查询 CloudBase `/v3/releases/latest`，验签后访问清单中的 artifact 入口。入口核对已发布记录，只返回 302，不调用 CloudBase 安装器存储、不读取或转发 EXE。
4. 客户端跟随跳转从 GitHub 下载 EXE，继续校验字节数、SHA-256，并交给既有更新助手。教师下载学生安装器后仍通过校内 LAN 分发。

应用内更新的外部源固定为 GitHub 仓库 `Ljc798/veyon-campus-deployment`；云函数只生成 GitHub Release 下载链接，不支持国内镜像回退。当前 GitCode 配置只用于手动 ZIP 镜像发布，不影响应用内更新。

CloudBase 仍有小量版本查询、心跳、数据库及跳转请求的用量，不能称为零用量；每个约 128 MB 的 EXE 下载由外部站点承担。校区配置 ZIP 的存储与手机号校验下载流程保留。旧 application-release-artifacts 桶和数据库 object_key 字段为历史结构，当前应用安装器发布/下载均不使用该桶，本轮未删除历史数据。
