# Veyon Campus 1.1.89

本次处理“课堂还没结束，网站限制就自己解除了”的两个独立成因：自动解除时间仍然按教师端进程启动时间算，以及学生端报“策略已禁用”时教师端直接把它当成解除。

## 自动解除时间：只在没选过时才重新计算

`自动解除` 的“现在 + 1 小时”**只是没选过时间时的兜底默认**，不是固定时长；教师选的 15:30、两节课后、任何自定义截止时间都优先。问题在于这个兜底值过去在教师端进程启动时算一次、之后整天沿用：08:20 打开的教师端，把 09:20 带进 09:10 开始的课堂，于是十分钟后限制就到期了——表现出来就是“过几分钟自动解除”。

1.1.89 起：

- **教师选过的截止时间一律不动**，即使已经过期。过期时通过按钮禁用原因提示重新选择，不再偷偷改掉教师的时间。
- 只有“从未选过”的兜底值会在**开始课堂时**重算；课堂进行中已发布的截止时间不会被后续刷新缩短。
- 手机端下发如果没带截止时间，会继承本堂课仍然有效的截止时间，不再把教师自定义的 15:30 悄悄换成“当前时间 + 1 小时”。

## 学生端报“已禁用”不再等于解除

课堂页读取学生机状态时，只要学生端回一句“网站策略是 Disabled”，教师端就清掉归属、把那一行显示成 `已解除`。这种回答可能来自学生机时钟偏快（签名策略里的 `ExpiresUtc` 在它那边已经到期）、策略被第三方清理，或学生端刚重启——无论哪一种，课堂其实还在进行。

现在只有在**恢复任务**或**确实到达截止时间**这两种情况下才允许结束归属；其余情况保持归属并把该设备重新排入下发队列，同一轮里立即重推，不需要等退避。行内文案会写明：

- `学生端报告网站限制已不存在，但本堂课仍在进行（截止 HH:mm），已重新下发。`
- 若学生端记录了到期时间：`学生端记录的到期时间是 HH:mm:ss（本机未到截止时间，说明学生机时间偏快）。`
- 若签名状态里带回的学生端时间与教师机相差超过 2 分钟：`该机时间比教师机快/慢约 N 分钟，自动解除会提前触发，请校正学生机时间。`

另外，签名策略里的 `IssuedUtc` / `ExpiresUtc` 原来用的是教师机时间，学生端会拿自己的时钟检查：时间稍快就会把刚收到的策略判成“已到期”，稍慢则会把刚签发的策略判成“来自未来”，两种都拒绝应用。1.1.89 从学生端**签名状态回执**取它的时钟，把策略的两个时间一起平移到那台机器的时间轴上；教师端的截止倒计时仍按教师机时间算，两边指向同一刻。偏差超过 30 秒时，行内详情会写明“已按该机时间偏差调整策略时间”。

## 建议的验证顺序

1. 教师端升到 1.1.89，先打开教师端、**等 10 分钟以上**再开始课堂，确认 `自动解除` 显示的是“开始课堂 + 1 小时”，而不是“打开教师端 + 1 小时”。
2. 开始课堂 → 启用网站限制 → 等到全部设备变成“策略已应用”，记录截止时间。
3. 在学生机上故意把系统时间调快 **3 分钟**（不要超过 5 分钟，否则签名状态请求本身会被判过期），再点一次“重推”。预期：那一行不会变成 `已解除`，而是出现“已按该机时间偏差调整策略时间……”，并且限制仍在。验证完请把学生机时间改回自动同步。
4. 若限制真的消失，看学生机注册表 `HKLM\SOFTWARE\VeyonCampus\WebsitePolicy` 的 `ExpiresUtc` 与 `ExpiredUtc`：两者的差值就是学生端提前了多久；教师端那一行的详情里也会写出这个时间。
5. 教师端 `%LOCALAPPDATA%\VeyonCampus\Teacher\classroom-quick-control.json.events.jsonl` 逐条记录状态变化的来源。若仍出现中途解除，取最后 20 条里对应设备 `desired=Release` 的那条，看是谁（`source` / `reason`）发起的。

## 说明

- 教师端不会替学生机改时间。学生机时钟偏差同时会影响更新签名校验与课堂状态，建议在教室机上开启“自动设置时间”。
- 手机端推送的并发与超时仍沿用 1.1.86 的取值，本次未改动。
