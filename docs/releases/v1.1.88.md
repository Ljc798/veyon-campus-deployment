# Veyon Campus 1.1.88

本次修复三个互相牵连的问题：教室快捷管控按钮“要过一次别的操作才变可用”、学生端静默更新失败后无法重试、以及教师端维护账本在时间戳相同的一次推进上直接报错。

## 教室页：按钮变灰不再需要“碰一下别的操作”

`启用网站限制`、`锁定键盘与鼠标` 两个按钮共用同一个可用性判定，但界面绑定了四个派生属性。部分刷新路径只发出了其中一两个变更通知，于是状态其实已经可用、按钮却还是灰的——直到点一次“锁定键鼠”触发了另一条刷新路径，才把漏掉的那个属性补发出去。

现在这组属性统一由一个方法一起发出：名单读取结果、课堂开始/结束、教室名单切换、范围待确认状态变化，都会同时更新按钮、禁用原因和悬停提示。按钮灰着时鼠标停上去，提示里写的就是六个前置条件中没满足的那一个。

## 学生端静默更新：一次失败不再卡死后续所有更新

学生端上报的是“当前没有未结更新事务”、版本仍是 1.1.86，但教师端维护账本把那次尝试停在“待验证”，于是：

- 界面显示“已记录 1 · 完成 0 · 待验证 1”，看起来像在等；
- 再点一次“一键静默更新”，会撞上“该设备已有活动维护操作；必须先恢复或核对原 operationId”，整批下发直接失败。

两个原因都已修掉：

1. **学生端签名状态的时钟比状态机粗**。`inProgress` 的那次读回和紧接着的 `committed`/`rolledBack` 读回会带同一个时间戳，账本的单调性校验把它当成“改写历史”而拒绝写入，事务就此停住。现在允许“前一条是 `inProgress`、后一条是终态”的同时间戳推进；其余同时间戳的改写仍会被拒绝。
2. **学生端已经忘掉、版本又没变的尝试会自动收尾**。下一次点击时，账本先把它标成失败并写明原因（“学生端没有该事务记录，安装版本仍是 1.1.86”），然后在同一次点击里重新检查、重新下发，不需要再手工清理 journal 文件。

## 建议的验证顺序

1. 教师端升到 1.1.88，打开“设备与更新”。
2. 直接点“一键静默更新全部学生端”：上一次卡住的 PC-01 应当先出现一条失败原因，随后立刻开始新的下发，而不是报“已有活动维护操作”。
3. 如果这一次仍然失败，看学生机上的两份材料：`agent-startup.log`（与该学生端 Agent 配置文件同目录）以及配置目录下的 `student-update-*` 暂存目录。前者记录 Agent 侧拒绝的原因，后者保存了事务日志和已下载的安装包。

## 说明

- 微信/手机端推送策略的超时与并发调整已在 1.1.86 发布，本次未再改动。
- 快捷管控的“提前自动解除”仍未修改：需要先确认学生机 `HKLM\SOFTWARE\VeyonCampus\WebsitePolicy` 里 `ExpiresUtc` 与 `ExpiredUtc` 的差值，判断是时钟偏差还是时长设置。
