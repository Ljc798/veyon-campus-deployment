# Veyon Campus 1.1.110

本次新增重点：**键鼠锁定支持多选学生一键执行 + 自定义截止时间 + 学生重启后自动恢复**。前面各节记录的是同一迭代链上陆续修好的问题（课堂自动解除、网络层封禁、DNS 误伤、身份核对、进程压制、推送失败可见、键鼠状态核验等）。本版核心改动见文末“十三、多选键鼠锁定与重启恢复”。

## 一、课堂进行几分钟后自动解除（按钮同时变灰）

课堂还在进行、截止时间明明写着 12:41，11:46 就显示“管控已解除”，详情是“解除命令后已读回网站限制为停用”。同时两个快捷管控卡片变灰，上方提示“课堂范围已经变化，请先确认切换到当前 Veyon 名单”。

根因是一处判定把两件不同的事合并了：

```
HasPendingClassroomScopeChange = 会话存在 && (
    选中了别的教室/校区
 || !IsActiveClassroomTargetSetCurrent      // ← 这里
)
```

而 `IsActiveClassroomTargetSetCurrent` 要读一份**三分钟内**的 Veyon 名单快照：

- 课堂开始后，只要目录读取超过 3 分钟没刷新，取不到快照就直接判定“目标集不是当前”；
- 这个判断返回 true 后，`ReconcileClassroomScopeAsync` 认为“旧课堂范围需要恢复”，对仍在管控的设备调用 `ReleaseClassroomQuickControlsAsync` —— 这就是那条解除命令；
- 同一个标志又让 `CanStartClassroomQuickControl` 变 false，于是按钮一起灰掉。

也就是说：**“无法验证名单”被当成了“名单变了”**，每过三分钟就把正在生效的策略撤掉一次。

1.1.95：

- 拆开两种语义：只有“确实选了别的教室/校区”，或“名单可读且确实不一致”才算范围变化；
- 名单快照过期/读取失败只表示“暂时无法核对”，不触发解除、也不禁用快捷管控（课堂目标在开始时已经固定在会话里）；
- 顺带修正了“没选中任何教室也算变化”的判断；
- 文案补上“课堂范围还在等待确认”分支，并增加兜底：**只要按钮被禁用就一定显示原因**，不会再出现灰控件配空白。

> 这条同时解释了之前两轮排查里的两个现象：按钮灰掉没有原因、以及“点锁定键鼠再取消又可以点”——后者是因为操作过程刷新了目录快照，让那条失效判断短暂恢复。

## 二、失败设备重试提示“没有选中学生机”

在“策略与预设”里推送策略，部分学生没开机所以失败；点“选择失败设备”把失败的机器勾上，再点推送，却提示没有选中学生机或没有填入 IP。

勾选是好的，问题在目标的“可信检查”：

- 从机房名单整批填入目标时，会记录一个 Veyon 目录快照，并要求**读取时间在 3 分钟内**；
- 第一次推送 150 台本身就可能超过 3 分钟；
- 重试时快照已过期，`GetSelectedWebsitePolicyTargets()` 直接返回空数组，`NormalizeTargets` 于是抛“请至少填写一个学生电脑名或 IP 地址”——看起来就像没选中。

1.1.95：

- “选择失败设备”勾选后不再要求目录快照：这些目标来自**刚拿到的签名推送结果**，不是可能过期的地点整批填充；
- 推送入口区分“真的没选”和“选好了但快照过期”，后者给出可操作原因（如“Veyon 名单已超过 3 分钟未刷新，请重新读取地点后再推送”），不再误导成未选中。

## 三、Agent 更新被 Maintenance 目录卡住

### 经过

维护服务（Maintenance Service）按设计在**校区配置目录**里创建 `Maintenance\`，存放自己的运行文件；Agent 更新/卸载前的归属校验（`VerifyAgentConfigurationRootIsSafe`）维护一份“允许删除的条目”清单，而清单里没有这个目录。于是产品用自己写的文件挡住了自己的更新，**只要那台机器装过维护服务，Agent 更新就失败**，与网络配置无关。

1.1.91 把 `Maintenance` 加进了清单，但当时对目录**内容**也做了文件名白名单。实际目录里不止 `maintenance-identity.json`：

```
maintenance-identity.json          维护服务签名密钥
maintenance-bootstrap.json         教师连接配置
teacher-connectivity-sync-recovery.json   教师连接变更的恢复记录
maintenance-replay-window.json     命令重放窗口
maintenance-update-transaction.json / maintenance-service-release-transaction.json   更新事务
UpdateStaging\                     签名安装包暂存
```

所以 1.1.91 在第二台虚拟机上又卡在 `maintenance-bootstrap.json`。

### 1.1.92 的做法：校验访问控制

不再逐个枚举文件名，改为**校验访问控制**：

- `Maintenance` 目录必须是 protected DACL，且只含 `SYSTEM` 与 `Administrators` 的完全控制；
- 递归检查其子项：不得是重解析点，每个子目录/文件的 ACL 也必须是这一组；
- 深度上限 4 层。

这个判断比文件名白名单更严格也更有意义：**只有 SYSTEM 和 Administrators 能往这个目录写东西，所以里面的任何文件都只能由产品自己产生**。反过来，文件名清单每加一个文件就要改代码，维护服务一升级就会再次卡住——1.1.91 已经证明了这条路走不通。

### 1.1.93 补的两处

1.1.92 的测试包在同一台机器卡在：

```
Maintenance 服务文件 ACL 未限制为 SYSTEM 和 Administrators：
...\Maintenance\maintenance-replay-window.json
```

两个原因：

1. **目录 DACL 是 protected，新建文件不继承任何 ACE。** 维护服务写重放窗口（`maintenance-replay-window.json` 和它的 `.lock`）时没有单独加固，所以它是这个目录里唯一一个“谁都能读”的文件——校验说得没错，是写入端漏了。
2. **只校验不修复**，所以已经装过的机器就算换成 1.1.92 也永远过不去。

1.1.93：

- 重放窗口的临时文件、目标文件与锁文件在写入前就设置私有 ACL，和目录里其它文件一致；
- 归属校验改为**先尽力加固再校验**：对每个文件尝试设置私有 ACL（被占用等情况下失败不致命），然后校验结果。旧机器上错误的 ACL 会被就地修正，不需要手工干预；
- 同时把 `IsRecognizedAgentConfigurationEntry`（判断配置目录下哪些条目属于产品）保留下来，并加了单元检查：`Maintenance` 是目录→通过、是文件→拒绝，以及 `health-repair`、`student-update-*`、各类临时文件与未知文件。

> 已经卡住的机器：直接装 1.1.93 再点“更新/修复 Agent”，不需要手工删目录。如果仍报 ACL 错误，说明文件正被维护服务占用，先停止服务再重试：
> ```
> sc stop VeyonCampusMaintenanceService
> ```

## 四、网站限制下沉到网络层

1.1.89 及以前，网络层只把黑名单域名解析成 IP、在 Windows 防火墙里封这些地址。三个缺口：改 DNS、浏览器自带 DoH、白名单模式没有网络层。

- **改 DNS**：学生把 DNS 改成 `8.8.8.8`，解析到的是没被收录的 CDN 边缘 IP，封禁列表里没有，照样能开。
- **浏览器自带 DoH**：Edge/Chrome 的“安全 DNS”只在浏览器策略关闭时才听，学生新装一个浏览器就绕开了。
- **白名单模式没有网络层**：只允许名单内网站时，地址封禁是空的，网络层实际上什么都没做。

### 补的三层

#### 1. 强制 DNS（端口 53）

防火墙新增出站规则，范围取决于当前的策略模式：

| 模式 | 封谁 | 为什么 |
|---|---|---|
| 黑名单 / 组合 | 只封**已知公共解析器**（Google、Cloudflare、Quad9、OpenDNS、AdGuard、Control D、AliDNS、DNSPod、腾讯、百度、114DNS 以及电信/联通/移动常用 DNS） | 黑名单是按**目标地址**执行的，换解析器改不了已封的地址；把整个公网 53 全封掉只会误伤学校自己的解析器 |
| 白名单 | 除本机解析器外的**全部公网 53** | 白名单靠“解析结果”执行，必须堵住任何换解析器的路径 |

两种模式都会：

- 放行私有网段（`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`127/8` 等），局域网网关、校内 DNS 不受影响；
- 把本机当前使用的 DNS 服务器**从封禁段中扣除**（含 IPv4 与 IPv6、含所有已启用网卡）；
- 读不到 DNS 设置时**不启用** 53 封禁，只在教师端显示原因。

写入前还会做一次**解析器探测**：直接向本机配置的 DNS 服务器发一个 UDP 53 查询，没有任何一台响应就暂缓 53 封禁（DoH 仍然封锁），并在教师端写明原因。这样一份过期或不可达的 DNS 列表不会把学生机变成离线砖。

效果：学生把 DNS 改成 `8.8.8.8` 之后，出站 53 直接被拒，只能回落到系统 DNS（也就是 hosts 和浏览器策略生效的那条链路）。

#### 2. 封 DoH 端点（端口 443）

DoH 和普通 HTTPS 共用 443，没法按端口区分，所以维护一份已知 DoH 解析器的地址表，单独封它的 443（TCP + UDP，含 HTTP/3）：

Cloudflare、Google、Quad9、OpenDNS、AdGuard、CleanBrowsing、Control D，以及国内的 AliDNS（`223.5.5.5` / `223.6.6.6`）、DNSPod（`119.29.29.29` / `182.254.116.116`）、腾讯 DoH、百度 DNS。

这些地址只提供 DNS 服务，封 443 不会影响学校要用的网站。它们的 53 端口本来就已被上一条覆盖。

**本机正在使用的解析器会从 DoH 名单里剔除。** Windows 11 会自行把已知解析器升级成 DoH，如果把学校正在用的那台也封掉 443，等于把本机自己的解析链路切断：已缓存的名字还能开，其余全部超时——表现就是“有的网站能开、有的打不开”。

#### 3. 白名单模式也获得 DNS 强制

“仅允许指定网站”过去在网络层是空的。现在即使地址封禁为空，DNS 强制和 DoH 封锁仍然会写进去——学生无法通过换解析器把不在名单里的网站解析出来。

真正的“只允许名单内”还需要反向封禁（默认拒绝 443/80，只放行名单 IP），这一层风险更大（会波及 Windows 更新和教师端自己的通道），单独排一轮，不混在本次发布里。

## 五、策略生效期间个别网站打不开

没到解除时间、策略仍在，但输入某些网站打不开，换一个又能开；结束课堂就全部恢复。这确实是 DNS 强制引起的，1.1.90 的实现里有两个缺陷：

**1. 把本机自己的解析器也封了 443**
DoH 端点表里包含 `223.5.5.5`、`119.29.29.29` 这类国内公共 DNS，而学校经常直接把它们当普通 DNS 用。53 端口虽然放行了这台地址，443 却仍然被封——Windows 11 一旦把这些解析器升级为 DoH，解析就走 443，于是被自己的规则切断。已缓存的名字还能打开，没缓存的一律超时，正好是“有的能开、有的不能”。

1.1.95：**本机当前使用的解析器一律不进 DoH 封禁名单**。

**2. 黑名单模式也封了整个公网 53**
“封掉除本机解析器以外的全部公网 53”对白名单是必要的，对黑名单则是过度：黑名单按目标地址执行，换解析器并不能让已封的地址变得可达。但这条规则会连带封掉某些软件自带的解析器（游戏启动器、教学工具、驱动组件），它们解析失败，用户看到的就是“我输入的这个网站不行”。

1.1.95：黑名单/组合模式只封已知的公共解析器；白名单模式保留全封。

**3. 新增解析器探测**
见上一节。DNS 列表过期、或某台服务器只在别的网段可达时，53 封禁会被自动暂缓，不会出现“整台机器解析不了”。

> 仍然存在的一种误伤：把**共用 CDN 边缘 IP** 的站点加入黑名单时，同一个 IP 上的其它网站也会连不上。这类站点由 hosts 与浏览器策略按域名精确拦截，网络层只能按 IP 拦，做不到区分。遇到“某个与被禁站点无关的网站也打不开”，先结束课堂确认是否恢复，再看教师端那一行的封禁地址数。

## 六、学生机重启后，解除要等好几分钟

### 现象

学生机重启后策略仍然生效（这是对的，Agent 会恢复），但教师端点“一键恢复全部”报失败、状态一直是“等待上线 / Agent 暂不可达”，过了几分钟才自己好。同一时间教师端还能和学生端互发消息。反过来，**先关机再推送，开机后反而很快就生效**。

### 原因

消息走的是 Veyon 通道，快捷管控走 Agent 的 HTTP 通道。重启后 Agent 还没起来的那几十秒里，每次尝试都会失败，而失败退避是**指数增长**的：

```
60s → 120s → 240s → 480s → … 上限 30 分钟
```

所以第一次失败后等 1 分钟，第二次 2 分钟，第三次 4 分钟——Agent 早就起来了，教师端却还在这条梯子上等着。这也解释了为什么“关机时推送、开机后很快就好”：那次是 Agent 启动后按顺序领到的任务，没有走退避。

### 1.1.96

- **离线不再按“失败”退避**：`Phase = WaitingForAgent` 时改为 **10s → 20s → 30s（封顶）**，真正的失败（签名不符、状态冲突等）仍走原来的长梯子。
- 补推循环的间隔从 30 秒降到 15 秒；同一台设备的检查上限 30 秒。
- 读旧状态文件时也套用这个上限：升级前写下的“几十分钟后再试”会被就地纠正，不用手工清状态。
- 解除、锁定这类命令在设备离线时的汇总文案改为“**已排队：N 台设备暂未上线，约半分钟内自动重试，上线后自动完成，无需重复点击**”，不再让人以为命令失败。

### 顺带修的问题

启用按钮的悬浮提示在可用时是一个**没有文字的白色空框**：绑定值原本是空字符串，Avalonia 对空字符串也会画气泡。现在没有原因时返回 `null`，不再弹空框。

## 七、已经开着的应用拦不住

### 现象

学生的抖音设置了开机自启动，或者课间就打开了客户端；上课时教师端点“启用网站限制”，学生照样能刷。浏览器里已经打开的页面也一样。

### 原因

防火墙规则决定的是**新连接能不能建立**。Windows 不会因为出现一条阻止规则，就把**已经建立**的 TCP 会话拆掉。所以：

- 开机自启动的客户端在策略下发前就连上了 CDN，会话一直保持着，视频继续流；
- 课间打开、上课才推送的也一样，连接早就建好了；
- 而“关机时推送、开机后生效”之所以正常，是因为那时客户端还没建立任何连接。

规则本身没错，缺的是“让已经存在的连接立刻失效”。

### 1.1.97：断开已有的 TCP 会话

网络层写入成功后，Agent 会枚举本机 TCP 连接，**把远端地址已经落在这个封禁集合里的会话直接重置**（`SetTcpEntry` + `MIB_TCP_STATE_DELETE_TCB`）：

- 只匹配已经在封禁集合里的地址，不会波及学校要用的站点；
- 客户端随后重连——连的是被封的地址，防火墙直接拒绝；重新解析则命中 hosts（返回 `0.0.0.0`）；
- 只处理 IPv4；IPv6 目标本来就是逐包丢弃，不存在“旧会话”问题；
- hosts 写入后本来就会刷新系统 DNS 缓存（`DnsFlushResolverCache`），已开着的程序重新解析时看到的是新映射。

### 1.1.100：UDP / QUIC 也一起断

1.1.97 之后仍有人反馈“还是要退出抖音再打开”。原因是**抖音这类客户端走 QUIC（UDP 443）**，而 UDP 没有会话可以重置：`SetTcpEntry` 只作用于 TCP；Windows 又会继续转发已经建立、状态仍匹配的 UDP 流。于是规则写对了、TCP 也断了，视频还在放。

1.1.100 在 TCP 重置之外，对每个被封地址加一条 **/32 主机路由**（下一跳 on-link，即交给出口网卡、而网卡上没有这个邻居），让发往该地址的包**当场无处可去**：

- UDP 没有重传通路，QUIC 立即失败；TCP 的后续包同样发不出去；
- 只对封禁集合里的地址加，且只接受 `/32`，`/24` 这类前缀会被拒绝，不会误封整段；
- 路由记录保存在 `HKLM\SOFTWARE\VeyonCampus\WebsitePolicy\BlockedAddressRoutes`，每次策略变化和卸载都会**先清旧再重建**；重复下发同一份名单时不会重建（否则封锁会闪一下）；
- 记录缺失或写不进去时**不装路由**——宁可少一层，也不留下一条删不掉的黑洞；
- 学生手工 `route delete` 掉的路由，下一次下发会补回来。

> **这一项在 Agent 里，学生端必须升到 1.1.100（Agent 0.4.65）**。只升教师端，连 TCP 重置都没有，现象和 1.1.96 一样。

### 1.1.110：域名和地址之外，再按进程压制

即使 UDP 也断了，靠“域名 → 地址”仍然追不上这类客户端，原因是结构性的：

- 客户端自带解析器和内置地址表，根本不经过系统 DNS，域名层对它不可见；
- 教师机与学生机被 CDN 调度到**不同边缘节点**，教师机解析出来的 IP 往往不是学生机实际连的那个；
- 地址封禁是“快照”，客户端换节点、换域名、走 IPv6 就绕开了；
- 而进程是确定的：**学生要看抖音，就必须运行 douyin.exe**。

所以 1.1.110 增加了一层“按进程压制”：

- 策略限制哪个站，就关闭属于它的客户端进程。内置映射很克制：`douyin.com` → `douyin` / `douyinlive` / `douyinlauncher` / `douyinpc`，另有 `kuaishou.com`、`xiaohongshu.com`、`weibo.com`、`bilibili.com`、`huya.com`、`douyu.com`；
- 策略写成功后**立刻**结束一次，不等下一轮；之后 Agent 每 1.5 秒复查，起来就再关——开机自启动、课间打开、推送前就在播，三种情况都一样；
- 黑名单模式只关“名单里点到的站”的客户端；白名单模式关掉所有不在允许名单里的；综合模式按黑名单走，允许名单里的例外优先；
- 策略到期、解除、结束课堂 → 名单清空，不再关闭。没有限制的机器完全不受影响。

这样“必须退出抖音再打开才断”就不再是问题：应用连连接的机会都没有。

> 边界：学生把 `douyin.exe` 改名仍可绕过，这属于对抗行为，需要应用白名单（AppLocker/SRP）才能彻底封死；映射里的进程名与其它软件重名时会误关，目前选的都是独占名。

## 十、推送被拒绝时只显示“需核对”，看不到原因

### 现象

课堂中启用网站限制，设备行显示“网站状态需核对 / 策略已发送但没有取得匹配的新鲜签名读回”，上方提示“有设备需核对”，但**没有一句话说明学生机为什么没接受**。

### 原因

推送结果被丢弃了：

```csharp
_ = await WebsitePolicyTransport.PushAsync([binding.Target], signed, ...);
```

学生机明确拒绝（HTTP 409）时也照样往下走，然后读回自然对不上版本，于是统一落到“没有取得匹配的新鲜签名读回”。而 409 的正文里本来写着真实原因：身份指纹变了、版本不是更新版本、到期时间无效、诊断编号等。

### 1.1.110

- 保留推送结果，**失败就直接把学生机返回的原因显示在设备行**（带诊断编号），不再用笼统文案盖住；
- 推送成功但读回仍是上一版的，等 800ms 再读，最多两次——把“刚写完还没落盘”的竞态当成正常成功，而不是让老师去判断。

### 如果还是失败，先看这一行

学生机上打开：

```
C:\ProgramData\VeyonCampus\WebsitePolicy\<校区哈希>\agent-runtime.log
```

末尾如果出现 `operation-failed id=... operation=网站策略应用`，往下就是异常原文。最常见的是身份指纹不一致——在“设备与更新 → 安全与身份 → 核对并固定身份”重新固定即可。

## 十一、键鼠锁定仍然报“状态无法核验”

### 现象

课堂中点“锁定键盘鼠标”，设备行出现“键鼠需核对 / InputGuard 当前状态无法核验；没有修改键鼠锁定”，键鼠完全没有被锁。

### 这条链路的构成

```
教师端 --签名命令--> Agent(SYSTEM, Session 0) --命名管道--> InputGuard(学生会话) --BlockInput-->
```

`BlockInput` 只能在交互桌面会话里调用，所以 Agent 必须在学生会话里有一个 Guard 进程。Guard 平时由 Student Companion 启动，空闲不锁。

“状态无法核验”是一个**合并后的结果**，它至少覆盖三种完全不同的情况，而过去的文案把它们压成了一句：

1. 学生会话里根本没有 Guard 进程（Companion 没运行、或 Guard 启动后退出）→ 管道连接 2 秒超时；
2. **检测到多个活动交互桌面会话**——虚拟机常见：控制台会话 + 远程桌面会话同时 Active，旧逻辑为了不锁错会话直接放弃；
3. Guard 进程路径与会话和 Agent 期望的不一致（安装目录不同）→ 管道对端校验失败。

### 1.1.110 的改动

- **多个会话时优先控制台会话**：`WTSGetActiveConsoleSessionId` 在 Active 列表里时选它。课堂机是学生坐在机器前用，控制台就是“正确的那一个”；两个远程会话且无控制台时仍然拒绝（不猜）。
- **原因写进日志**：Agent 读不到 Guard 时，把管道客户端给出的原话写到
  `C:\ProgramData\VeyonCampus\WebsitePolicy\<校区哈希>\agent-runtime.log`，
  行首是 `note operation=input-guard-status`。同一原因只记一次，不会刷屏。
- **教师端文案补上可能原因**，并指向那份日志。

### 现场一分钟定位

在学生机上用学生账号运行仓库里的：

```
powershell -ExecutionPolicy Bypass -File scripts\diagnose-input-guard.ps1
```

只读，输出：会话列表、Guard 进程与路径、Companion 进程、命名管道、安装目录版本、监督日志尾部、Agent 日志里的 InputGuard 行。把这整段发回来即可判断是“Guard 没起来”还是“多会话”。

若输出显示 **未发现 Guard 进程**，说明 Companion 没有把它拉起来。

### 1.1.110：Agent 自己把 Guard 拉起来

Guard 平时由 Student Companion 启动，但这台机器可能根本没运行 Companion（没登录、被关掉、Guard 崩过）。过去这种情况下教师端永远只能看到“状态无法核验”，而学生端没有任何东西会去补救。

现在 Agent 读不到可用 Guard 时，会**以 SYSTEM 身份在学生会话里启动同一个受保护的可执行文件**：

- 先取会话用户令牌（`WTSQueryUserToken`），复制为主令牌，建用户环境块；
- 用 `CreateProcessAsUser` 在 `winsta0\default` 上启动 `--guard-server`；若计划任务令牌缺少
  `SeAssignPrimaryTokenPrivilege`（错误 1314），自动回退到只需要 `SeImpersonatePrivilege` 的
  `CreateProcessWithTokenW`；
- 只启动安装目录里的那一个路径，不接收任何外部输入；会话已有 Guard 进程时不再重复启动；
- 每次尝试至少间隔 30 秒，避免失败时反复拉进程；成功或失败的原因都写进
  `agent-runtime.log`，行首 `note operation=guard-launch`。

也就是说：即使 Companion 没运行，第一次点“锁定此机键盘鼠标”时 Agent 也会把 Guard 补上，随后这条命令就能落地。

### 上一轮（1.1.104，仍然生效）：特权、僵尸 Guard、冷启动

1. **特权没启用**：`WTSQueryUserToken` 要求调用令牌里 `SeTcbPrivilege` 已启用；计划任务令牌不一定启用，失败码 1314 看起来像“没有会话”。现在启动前显式启用 `SeTcbPrivilege`、`SeAssignPrimaryTokenPrivilege`、`SeIncreaseQuotaPrivilege`，未能启用的名字写进日志。
2. **僵尸 Guard**：租约线程判定“无法解除输入”后会关掉请求队列，但进程还活着、管道还监听、永远不回执。现在 Guard 会自己退出，Agent 读到“进程在但没回应”时先结束再启动。
3. **冷启动太短**：700 ms 单次读取改为 4×700 ms 轮询。

### 1.1.110：现场日志指出的三个真凶

1.1.104 的日志第一次把问题指出来了：

```
note operation=guard-launch  已在会话 1 启动 Guard（PID 7764）
guard-server.log             ConnectionRejected  Win32Exception Win32=5: 拒绝访问。
guard-server.log             ServerStarting    SessionId=2 Interactive=True
guard-server.log             ServerExited      Win32Exception Win32=291: 所有的管道范例都在使用中。
```

三件事同时存在：

1. **Agent 把 Guard 启到了会话 1，而学生桌面在会话 2。**
   `WTSEnumerateSessions` 报了两个 Active 会话（控制台 + 远程桌面），旧代码只挑“一个”，管道名对不上。
   现在：**每个活动会话都启动一个 Guard**，状态读取按控制台优先的顺序逐个询问，锁定/解除对**所有**可用会话一起执行——否则学生切到另一个会话就绕过了；读回优先返回“已锁定”的那个会话。
2. **Guard 验证 Agent 身份时被系统拒绝（Win32 5 拒绝访问）。**
   Guard 以学生身份运行，要去读 Session 0 里 SYSTEM Agent 的映像路径，普通用户令牌对 SYSTEM 进程没有
   `PROCESS_QUERY_LIMITED_INFORMATION`，于是每次连接都被判“不是 Agent”。
   现在：管道 ACL 已经限定只有 SYSTEM 和当前用户能连，再要求客户端会话是 0，就足以确定对端是 SYSTEM；
   映像路径改为**能读就比对、读不到就放行**（读到但不匹配仍然拒绝）。
3. **同一会话里起了两个 Guard，第二个撞上单实例管道（Win32 291）。**
   Companion 和 Agent 会同时尝试启动。现在 Guard 启动时先抢 `Local\VeyonCampus.InputGuard.<会话>` 互斥体，
   拿不到就写 `AlreadyRunning` 并退出，一个会话只会有一个。

另外 `guard-server.log` 记录 `ServerStarting`（带 SessionId 与是否交互）与 `ServerStopped`——有前者说明进程确实进了服务模式，没有就是根本没起来（权限、路径或运行时）。

### 1.1.110：`BlockInput` 返回 5，锁定命令被 Windows 拒绝

1.1.110 之前的所有版本，Guard 都跑起来了、管道也通了、命令也送达了，最后一步卡在：

```
锁定命令没有取得成功回执；保留租约编号以便核对。
Windows 未接受输入阻止请求（错误码 5）。
```

错误码 5 是 `ERROR_ACCESS_DENIED`。`BlockInput` 在**调用方无法操作当前桌面**时会这样返回，最常见的两种情况：

- 前台窗口的**完整性等级高于调用进程**（例如屏幕上有一个“管理员”窗口），UIPI 会挡住；
- 系统直接拒绝非提升进程操作输入桌面。

Guard 由 Companion 以**学生令牌**启动，属于中完整性，于是永远不够。

#### 改法

1. **Guard 改由 Agent 以 SYSTEM 身份在目标会话内启动**：复制 Agent 自己的 SYSTEM 令牌，用
   `SetTokenInformation(TokenSessionId)` 把会话改成学生的会话，再 `CreateProcessAsUser` 到
   `winsta0\default`。进程在学生会话、完整性是 System，`BlockInput` 不再受上面的限制。
   拿不到时回退到原来的学生令牌启动，并在日志里注明“BlockInput 可能被拒绝”。
2. **Companion 不再启动 Guard**：两个启动者互相打架（一个用户令牌、一个 SYSTEM），谁先占住会话
   就决定能不能用。现在只有一个启动者，即 Agent。
3. **Agent 启动时替换掉学生令牌的 Guard**：读到“进程存在但不是 SYSTEM”就结束它再以 SYSTEM 重启，
   不必等第一次锁定失败。
4. **Guard 自己也认输**：`BlockInput` 失败时把当前窗口站\桌面（如 `winsta0\default`）和错误码写进
   日志，然后主动退出，让 Agent 用更高权限重建——不会留下一个永远锁不上的进程。
5. **日志位置改为 `C:\ProgramData\VeyonCampus\InputGuard\guard-server.log`**：SYSTEM 的
   LocalAppData 是系统配置文件目录，用学生账号看不到；ProgramData 两边都能读，写不进去时回退。

> 副作用：Guard 现在以 SYSTEM 运行。它只做两件事——响应签名命令执行 `BlockInput`、写日志；
> 管道 ACL 仍然只允许 SYSTEM 和当前登录用户连接，且 Agent 侧的命令是签名校验过的。

### 1.1.110：`ServerStarting` 之后卡在“租约不匹配”的根因

这一版的现场日志终于干净了：`guard-server.log` 只有一行 `ServerStarting SessionId=2 Interactive=True`，
之前的 `Win32=5`（拒绝访问）、`Win32=291`（管道冲突）、`ConnectionRejected` 全部消失——Guard 起来了、
进交互桌面了、管道也通了。失败点转移到了状态机层：教师端显示“尚未取得足够的可信状态：InputGuard
续租未确认……当前签名状态中的租约与本次操作不匹配；没有发送命令”，也就是**激活成功、续租失败**。

根因是控制代次（epoch）被噪声触发翻转：

- 每 5 秒续租一次，每次续租都会把租约**到期时间往后推**；
- `ObserveGuardState` 原来把“到期时间变化”也算作状态变化，于是每次续租都翻转 epoch；
- 续租流程是“读状态拿 epoch → 用该 epoch 签命令 → Agent 执行前再读一次状态并校验 epoch”。
  机器有两个活动会话，两次读可能命中不同会话的 Guard，它们的到期时间略有差异，导致 epoch 在
  这中间被翻转，续租命令被判“状态已改变”而拒绝；
- 续租接连失败，20 秒租约到期，状态读回变成 unlocked，于是教师端报“租约不匹配”，并停止自动续租。

#### 改法

1. **epoch 只在真正的安全相关状态变化时翻转**——即阶段变化（解锁↔锁定）或租约编号变化。
   到期时间只是元数据，续租刷新它不该翻转代次。命令成功后若代次未变，仍会主动翻转一次，
   防重放的安全性不变。
2. **续租/解除的状态预检查加两次短重试**（间隔 350ms，仿照网站读回）。一次瞬时读回不匹配
   不再让整个续租循环停摆；激活不重试，避免误开第二个租约。
3. **加双会话状态快照日志**：Agent 每 10 秒把每个活动会话 Guard 的阶段/租约/在线情况写进
   `agent-runtime.log`，行首 `note operation=input-guard-sessions`；状态跃迁写
   `note operation=input-guard-state`。签名状态协议只能带聚合结果，这两行让“s2 锁了、s1 没锁”
   这类双会话问题下次可以直接从日志看出来。

> 这版不碰启动、权限、管道——那些已经修好了。如果你的机器仍失败，请把 `agent-runtime.log` 里
> `input-guard-sessions` 和 `input-guard-state` 的行发回来，就能一次定位是哪个会话、哪种状态导致的。

### 1.1.110：真正的根因——网站策略阻止了键鼠锁定

加了快照日志后，现场一次定位。日志显示：

```
08:57:23  input-guard-state  phase=Locked,  lease=81df4748…
08:57:57  input-guard-state  phase=Expired, lease=null
08:57:57  input-guard-sessions  aggregate=Locked  s2=Locked/lease:81df4748/up
```

Guard 一直好好地锁着（s2=Locked），但教师端在锁定后 6 秒就报“续租未确认”，续租停摆、
20 秒后租约 Expired。问题不在 Guard、不在会话、也不在 epoch——而在 Agent 的命令入口。

根因是一条 v1.1.33 时代的遗留拦截，位于 Agent 处理 InputGuard 命令的地方：

```
如果学生机上存在网站策略（mode != Disabled），
就直接拒绝键鼠锁定的“激活”和“续租”命令。
```

那时“课堂模式”和“键鼠锁定”是二选一的，所以写了这条互斥。但从 1.1.103 把键鼠锁定改成
**按单台、与网站限制独立并存**之后，教师端的代码明确是“申请键鼠租约时，现有网站策略保持不变”。
两条规则自此互相矛盾：教师端推了网站限制 → 学生机 Registry 里留下非 Disabled 策略 →
之后任何键鼠锁定的激活/续租都被 Agent 拒绝。第一次锁定偶尔赶在策略写入前成功，续租时策略
已生效就被拒，于是“租约不匹配 → 停续 → 过期”。

#### 改法

1. **移除这条遗留的互斥拦截**：网站限制与键鼠锁定是两个独立控制，各自有独立的到期与释放，
   互不(gate)。这正是你要的“网站限制可以一直上课用，键鼠想锁哪台锁哪台”。
2. **新增命令结果日志**：每条 Activate/Renew/Release 的执行结果（动作、结果、阶段、租约、详情）
   写进 `agent-runtime.log`，行首 `note operation=input-guard-command`。以后命令被拒，日志里
   直接写明原因，不必再靠猜。

> 1.1.107 的 epoch 加固与双会话快照日志仍然保留——它们修掉的是真实的竞态与可观测性问题。

### 1.1.110：真正让租约活不过 5 秒的那一行

加上命令结果日志后，现场一次定位。日志显示：

```
09:16:36.77  input-guard-state   phase=Locked, lease=fdc5ee2a…
09:16:36.78  input-guard-command Activate: Succeeded, phase=Locked
09:16:36.83  input-guard-sessions s2=Locked/lease:fdc5ee2a/up
09:16:41.84  input-guard-state   phase=Expired, lease=null     ← 仅 5 秒后
```

Guard 锁得好好的（s2=Locked），但**租约时长 20 秒，却在第 5 秒就 Expired**；整段日志只有 Activate、
没有 Renew——续租命令在教师端读回时已经被判 Expired，根本没发出去。这与虚拟机无关，是 Guard
租约线程里的一处确定性缺陷。

根因在 `StudentInputGuardServer.RunLockThread`：

- 租约线程用 `GetLeaseWaitMilliseconds()` 计算等待时间，但这个函数把结果**封顶在 1000ms**，
  本意是“每秒醒一次、保持响应”；
- 而 `TryTake` 因这 1 秒上限超时后，代码**无条件调用 `ExpireLease()`**，把租约当成到期释放；
- 于是每次 Activate/Renew 之后约 1 秒，租约就被误判过期、键鼠被解锁。5 秒后出现 Expired，
  只是因为期间续租/状态请求让线程没走到那次超时分支，第一次空档就释放了。

#### 改法

- `TryTake` 超时后先判断**绝对到期时间**是否真的已过（`_leaseExpiresTimestamp`），没到就继续等；
  只有到点才 `ExpireLease()`。这样租约能完整活到 20 秒，或在续租成功后再续 20 秒。
- 这是键鼠锁定从第一版起“锁几秒就失效”的真正总根因——之前每一版修的都是外围（启动、权限、
  管道、会话、epoch、网站策略互斥），这一行才是锁不住的核心。

> 如果这版之后键鼠能稳定锁住、点解除立即恢复、关教师端 20 秒自动释放，那这条链路就完整闭环了。

## 八、学生端“移除学生端限制”之后身份对不上

### 现象

在学生部署工具里点了“移除学生端限制…”，重新安装后教师端提示身份/指纹不一致，课堂快捷管控和学生事件通道都拒绝连接，但找不到重新配置指纹的地方。

### 原因

“移除学生端限制”会删除校区配置目录，连带删掉其中的 `agent-identity.json`——那是这台学生机的 **Agent 身份私钥**。重装时会生成一把新密钥，指纹自然变了。

教师端为了防冒充采用**首次信任**（TOFU）：第一次收到有效签名时把公钥固定下来，之后必须与该指纹一致。密钥变了就不会自动接受，也不会静默覆盖——这是设计如此，缺的只是“在哪儿重新确认”。

### 教师端在哪里重新确认

**位置一（推荐，能看到新旧指纹）**：`设备与更新` → 点选那台学生机，展开详情 → “安全与身份” → 点 **“核对并固定身份”**。会弹出对话框列出旧指纹与新指纹，确认后写入信任记录并重新读取签名状态。

1.1.99 起：

- 这个按钮**一直显示**，不再只在“确实存在身份差异”时出现，事后想复核随时能点；没有差异时会直接说明“身份与已固定指纹一致”。
- **Agent 离线也能核对**。原来点这个按钮会先向学生机要一次实时身份，机器关机、或正在被其它读取占用时就拿不到，按钮看起来像“点了没反应”。现在实时读取失败时改用**最近一次有效签名回执里的身份**（同样是学生机签过名的），核对码对得上就能固定；固定后告警立即消失，该机下次回执到达时自动复核。
- 从告警卡片点“查看设备”会**自动展开**那一行，不用再自己找展开箭头。

**位置二（批量）**：`设备与更新` → 勾选学生机 → “同步教师连接配置”或“一键静默更新全部学生端”。这两条流程会逐台核验身份，并在教师明确操作后**自动批准密钥变化**，状态栏会显示“密钥变化已批准 N 台”。

**位置三（应急）**：教师端本机删除该条信任记录，下次通信会重新首次固定：

```
%LOCALAPPDATA%\VeyonCampus\StudentAgentTrust\agents.json
```

只删对应 `target` 的那一条，不要整份删除——那是所有学生机的信任清单。

### 1.1.98 / 1.1.99 的改进

1.1.98 把路径写进了提示；1.1.99 让入口常驻并且能离线核对（见上）。

> 维护服务的身份是另一套密钥（`Maintenance` 目录），它的轮换在 `设备健康` → “维护服务密钥轮换”里用“核对并批准轮换”处理，与本节的 Agent 身份不是同一个。

## 十二、键鼠锁定改为按单台执行

### 为什么要改

网站限制是“全班一起”的语义：一节课的规则对所有机器一样，教师点一次就该覆盖全班。

键鼠锁定不是。它把学生正在用的机器**整个冻住**——键盘、鼠标、快捷键全部失效。一次锁住全班意味着：

- 只要有一个人还在提交作业、或者在等一个下载，全班一起卡死；
- 只要有一台机器的 Guard 状态没核对上，整批结果就混着“已锁/需核对”，老师得逐条读；
- 解除时同样是一批，出问题的机器越多越难收拾。

真正需要的场景是“**这一台**在放视频/在打游戏，先冻住他”，而不是“全班停手”。

### 1.1.110 怎么改

- 课堂页顶部只剩“网站限制”一张卡片（全班），并注明键鼠锁定在下方逐台执行；
- “逐台执行进度”的每一行展开后新增两个按钮：
  - **锁定此机键盘鼠标**（该机当前没有本工具的租约时出现）
  - **解除此机键鼠锁定**（该机有租约或上次结果未核验时出现）
- 只对点中的那一台发命令（`selectedTargetIds` 一直是服务层支持的参数，只是界面没用上）；
- **不改变课堂的自动解除时间**：单台锁定不会把全班的截止时间顺手改掉（这是新增的 `preserveControlExpiry` 语义）；
- 本版起，单台锁定也支持下面的“持久化 + 自定义截止时间”（见第十三节）。

> 手机端目前仍是课堂级的键鼠按钮，尚未改成按设备或批量；桌面端的逐台/批量入口是本版新增。

## 十三、多选键鼠锁定与重启恢复（本版核心）

前面所有键鼠锁定都是“内存态 20 秒租约 + 教师端每 5 秒续租”，它有两个结构性问题：

1. **教师端续租失败即永久停止**（读回一次不匹配就 `RemoveRenewableLease`），学生机一重启，续租永远停在那台机器上；
2. **catch-up 只补网站策略，不补键鼠**，所以没有“上线后自动重新锁定”这条路。

结果就是：学生**重启一次就能逃过键鼠锁定**——这正是机房里最常见的绕行方式。

### 怎么改

- **学生端 Agent 持有“锁定意愿”**：教师锁定成功后，Agent 把 `{租约号、自定义截止时间}` 写入受保护配置文件（仅 SYSTEM / Administrators 可读写，学生改不了）。
- **Agent 自己维持租约**：每 5 秒本地续租，不再依赖教师端的续租循环。教师端关掉、断线，锁都保持。
- **重启自动恢复**：Agent 开机（SYSTEM 计划任务）读到意愿，等交互桌面就绪后，先给 **45 秒宽限期**让学生登录进桌面，然后自动重新锁定，一直持续到自定义截止时间。
- **宽限期只锚定一次**：写进配置，学生反复重启不能把 45 秒无限往后推。
- **只有两种结束方式**：教师点“解除”→ 立即清除意愿并放行；到达自定义截止时间 → 自动放行。这样既“一直锁得住、想停就停”，又由绝对截止时间兜底，不会无限锁死。

### 教师端怎么用

- 逐台执行进度上方新增**批量栏**：每行左侧勾选用来自定义多选，支持“全选”。
- 选好机器后填**“键鼠锁定到今天 HH:mm”**（默认 45 分钟后，最长 12 小时），点**“批量锁定所选”**；点**“批量解除所选”**立即释放。
- 单台行内的“锁定此机键盘鼠标”同样使用这个截止时间。
- 网站限制仍是全班一张卡片，与键鼠多选互不干扰；键鼠锁定不改变课堂截止时间。

### 验证顺序

1. 勾选 2~3 台 → 设一个几分钟后的截止时间 → 批量锁定：这几台应被锁住，其他机器不受影响；
2. 重启其中一台：登录进桌面后约 45 秒，键鼠应自动重新锁上（不用教师再点）；
3. 到设定的截止时间：自动解锁；
4. 中途点“批量解除所选”：立即解锁；
5. 到点前反复重启同一台：宽限期不会重新开始计时。

## 教师端能看到什么

课堂页设备行的摘要新增一段：

- `DNS 强制已生效（仅放行 192.168.1.1；封 32 段公网 53、20 个 DoH 端点）`
- `DNS 强制未生效（换 DNS 或开 DoH 可绕过）`
- `DNS 强制未完全生效：未读取到本机 DNS 服务器……`（此时 DoH 仍然封锁）

旧学生端不上报这些字段，会显示 `DNS 强制未上报`，不影响其它状态。

## 验证顺序

1. 教师端与学生端**都**升到 1.1.110（学生端 Agent 为 0.4.75）。只升教师端看不到新增状态，只升学生端则 DNS 强制和进程压制不会写入。
2. 开始课堂 → 启用网站限制（黑名单模式，随便加一个站点），等设备行出现“网络层已封 … 个地址”。
3. 在**学生机**上打开 `cmd`：
   ```
   nslookup www.baidu.com 8.8.8.8
   ```
   预期：超时 / 无响应（53 到 8.8.8.8 被封）。再执行 `nslookup www.baidu.com`（用系统 DNS）应正常返回。
4. 在学生机上把网卡 DNS 手动改成 `8.8.8.8`，再访问任意网站。预期：解析失败，网站打不开；把 DNS 改回“自动”后恢复。
5. 在学生机浏览器里打开“安全 DNS / DoH”并选择 Cloudflare，访问被禁网站。预期：仍打不开（443 到 1.1.1.1 被封，回落到系统 DNS 后 hosts 生效）。
6. 教师端那一行应显示 `DNS 强制已生效（仅放行 …；封 N 段公网 53、M 个 DoH 端点）`。
7. **身份核对**：在“设备与更新”里点选一台学生机并展开详情，“安全与身份”下方应**始终**有“核对并固定身份”；在有身份差异时点它，弹出旧/新指纹，勾选后固定，该行与上方告警立即更新。把学生机**关机**再点一次，也应能弹出对话框完成核对（用最近一次有效回执里的身份），不再出现“点了没反应”。
8. **已连着的客户端**：学生机开机后先打开抖音（或任意视频客户端）播放，再在教师端点“启用网站限制”。预期：**客户端在 2 秒内被关闭**，再次打开也会在 1.5 秒内被关闭；结束课堂后可以正常启动。
9. **推送失败可见**：把一台学生机的身份指纹换成别的（或在名单里填一个无法解析的域名），再推送。预期：设备行直接显示学生机返回的原因和诊断编号，而不是“没有取得匹配的新鲜签名读回”。
10. **键鼠锁定（按单台）**：在“逐台执行进度”里展开一台学生机，点“锁定此机键盘鼠标”。预期：只有这一台键鼠失效，其他机器照常；20 秒内应变为“键鼠锁定已核验”。再点“解除此机键鼠锁定”应立即恢复。若状态仍是“无法核验”，在学生机跑 `scripts\diagnose-input-guard.ps1`，并把 `agent-runtime.log` 里 `input-guard-status`、`guard-launch` 两行一起发回来。

## 回退

- 在教师端结束课堂或解除网站限制，会同时清掉地址封禁、黑洞路由、53 封禁和 DoH 封锁。
- 若解除后某个站点仍然打不开，检查是否有残留的主机路由（正常情况应为空）：

  ```
  route print -4 | findstr /r "255.255.255.255.*On-link"
  ```

  本产品添加的路由都指向出口网卡、掩码为 `255.255.255.255`，记录在
  `HKLM\SOFTWARE\VeyonCampus\WebsitePolicy` 的 `BlockedAddressRoutes` 里；重装或卸载 Agent 会清掉它们。
- 若某台机器因 DNS 配置特殊被误封，结束课堂即可让教师端下发解除；也可以在管理员命令行删除本工具的规则：

  ```
  netsh advfirewall firewall show rule name=all | findstr /i "VeyonCampus"
  ```

  确认列表后按前缀逐条删除，例如：

  ```
  netsh advfirewall firewall delete rule name="VeyonCampus Resolver Lock v4 TCP 000"
  ```

- 规则名以 `VeyonCampus Resolver Lock`、`VeyonCampus DoH Block`、`VeyonCampus Website Block`、`VeyonCampus Encrypted DNS Block` 开头，只删这些前缀即可，不影响学校自建规则。

## 说明与限制

- **代理 / VPN 仍然管不到**：目标地址变成代理服务器，本机规则看不见真实目的地。要根治只能把策略放在出口网关，这需要网络设备权限。
- 封 443 到 DoH 端点意味着这些 IP 上的普通网页也打不开。这些地址只做 DNS，属于可接受代价。
- 53 封禁依赖防火墙服务（`MpsSvc`）与学校防火墙策略。如果第三方安全软件接管了出站流量，教师端会显示“网络层封禁未生效”，此时 DNS 强制也可能被绕过。
- IPv6 同样处理：`2000::/3` 的 53 被封，本机配置的 IPv6 DNS 单独放行。
- 进程压制按映像名匹配：学生把 `douyin.exe` 改名即可绕过。要堵死这条路，需要应用白名单（AppLocker / SRP），属于另一个开关，本版未做。
- 键鼠锁定按单台执行，且 `BlockInput` 不拦截 `Ctrl+Alt+Delete`：学生按安全桌面可以恢复输入。这是 Windows 的设计边界，不是本产品的缺陷。
